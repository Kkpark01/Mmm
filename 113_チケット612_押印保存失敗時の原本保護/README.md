# チケット612：MCM1011U 押印保存失敗時の原本保護

利用者の「コードを修正してほしい」という追加指示に基づく実装修正版。112は仕様書の差替案であり、本フォルダはアプリへ反映するJavaコードです。

## 対象ファイル・修正内容

`src/main/java/com/daifuku/mcm/service/Mcm1011uNatsuinService.java` の `stamp`・`replace`。

- 押印前の原本の更新日時を保存し、復元用ファイルに設定する。途中の保存失敗・DB更新失敗で復元する場合、内容・ファイルサイズ・更新日時を元に戻す。
- ファイルの置換が成功したかを記録する。使用中等で置換できなかった原本は復元し直さず、自分が作成した退避だけを除去する。不要な退避が残って再実行を妨げる問題も防ぐ。
- 復元処理の登録前に失敗した場合も、自分で作成した退避を後片付けする。以前から存在する退避ファイルは上書き・削除しない。
- 押印準備後に内容または更新日時が変わったファイルは置換を中止する。置換後に外部更新された場合は既存どおり上書きせず、原本退避を残してログで復旧を案内する。

## 原因と確認できた範囲

従来は原本のバイト列を新しい退避ファイルへ書き、DBロールバック時にその退避を原本へ移動していました。内容は戻りますが、退避を作った時刻が原本の更新日時となり、チケットの「更新日時が変わらない」を満たしません。受領版を使った同条件のローカル試験で再現し、修正版で解消を確認しました。

また、原本の置換に失敗した場合にも復元を試みるため、使用中のファイルでは復元にも失敗して退避が残る経路がありました。修正版では使用解除後の再審査まで確認しています。

「検証環境で承認できない」という現象そのものの発生原因は、実環境の例外ログ・保存先の権限・Excelの使用状態が未提供のため未確定です。本修正は保存に失敗した際の原本保護と再試行を修正するもので、保存先の権限不足などを解消するものではありません。

## 維持する既存動作

- 審査成功時は契約・添付を「審査中」から「承認中」へ進め、審査印と審査記録を保存する。
- 最終承認成功時は「承認中」から「承認済」へ進め、既存の審査印を維持して承認印を保存し、期間を有効化する。
- 保存・DB処理が失敗すれば既存のトランザクションで契約・期間・添付の更新を取り消す。成功時だけ既存の完了メッセージを表示する。
- 既存のエラー通知は維持する。仕様書で「エラー通知の文言・表示を試験対象から外す」ことと、実装からエラー通知を削除することは区別する。
- ファイルの保存先設定・命名・ダウンロード・削除・メール処理は変更しない。

## 実施済み検証

- 最新本体405 Javaファイルに110・111・113を組み合わせてコンパイル合格。
- ローカルWindows上の実ファイル、Springの実トランザクションプロキシ、H2で84判定合格。
- 実Service・ControllerとRepositoryの実際の更新SQLを使用。検索・ロック行の取得は試験用Repository、権限情報・メール準備は試験用の代替。SQL Serverのロック・ネットワーク・実画面を検証したものではない。
- 審査成功（xls）、最終承認成功（xlsx）、原本使用中、使用解除後の再実行、複数添付の2件目保存失敗、審査／承認のDB更新後失敗、既存退避保護、外部更新保護、トランザクション外実行拒否を確認。
- 失敗時は契約・期間・添付の状態と監査項目、原本の全バイト・更新日時・サイズを比較。失敗時の完了メッセージ非表示、成功時の完了文言も確認。

## 検証環境で残る確認

1. 審査中の契約と添付Excelを用意し、**サーバー上の実ファイル**の更新日時・サイズ・押印欄、DBの契約／添付の承認状態と審査記録を控える。ダウンロードしたコピーの日時を代用しない。
2. 管理者と調整した検証専用ファイルで保存失敗を再現し、「審査・承認」を実行する。Excelを開くだけで必ず保存失敗するとは限らないため、失敗の発生をサーバーログで確認する。
3. 完了メッセージがなく、再検索後も「審査中」、DBの状態・審査記録が不変、サーバー原本の内容・更新日時・サイズが不変であることを確認する。
4. 失敗条件を解除して同じ申請を再実行し、「承認中」への遷移と審査印の保存を確認する。

実SQL Server・検証サーバー共有フォルダ・実ブラウザーは未確認です。DBとファイルは同一のトランザクション資源ではありません。サーバー強制停止、DB終了状態不明、復元時の権限喪失、外部更新がある場合は自動復元を保証できず、既存どおり退避とログによる管理者復旧が必要です。
