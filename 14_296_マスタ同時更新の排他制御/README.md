# #296 マスタ登録の同時更新対策

最新版 src (5).zip を基にした差分です。元の `mcm-web/src` は変更していません。

## 対象と変更内容

- MCM0011U 納入先：表示時の更新日時を条件に保存。保存後の排他キーはDBから取得し、JPAキャッシュの古い日時を次の保存に使わないように修正。
- MCM0012U プラント・ブランド構成：更新日時を確実に変更。ブランド構成のJPA保存・監査処理が排他キーを戻さないよう修正。
- MCM0013U 機器構成・機器明細・個体管理：既存の画面日時比較に加え、日時を条件にしたSQL更新で対象行を確保してから保存・削除。途中で競合した場合は同一トランザクションの更新を取り消す。
- 納入先・プラントで未定義だった専用メッセージを追加。機器構成の文言もチケット指定に統一。

表示文言：他のユーザがデータを変更した可能性があります。処理をやり直してください。

既存srcにも排他チェックはありますが、保存する日時の精度、JPAと直接SQLの混在、未定義のメッセージに不足がありました。本差分はその補強です。

## 確認結果と限界

- 最新srcのJava 386ファイルをコンパイルし、差分Javaもコンパイル成功。
- ローカルH2・Hibernate/JPA・JDBCの実トランザクションで20項目成功。リポジトリ呼出しはテスト用にEntityManagerへ接続し、機器構成の入力・参照マスタ検証は分離。
- 納入先・プラント・機器構成の古い画面からの保存拒否、先行更新の保持、最新日時での再保存を確認。
- ブランド構成の競合によるプラント更新の取り消し、機器明細の競合による構成数量の取り消し、個体管理の競合、JPAキャッシュが古い場合のSQL拒否を確認。
- 実際のメッセージ定義、秒精度の更新日時、既存日時NULLの競合も確認。
- 元srcの503ファイルは更新履歴のハッシュと一致。

会社のSQL Server・ブラウザを使った結合テストは未実施です。SQL Server固有のロック挙動、トリガー、別システムからの更新については実環境で確認してください。検証コード・ログは `検証記録/review_20260915/296` にあります（反映不要）。

更新日時を排他キーとして兼用するため、秒精度でも必ず値が変わるよう、現在時刻が前回日時以下なら前回より1秒進めます。短時間に連続更新した場合、表示用更新日時が実時刻より少し先になる場合があります。DBの独立したrowversion列を導入する方式は、この差分の対象外です。

## 会社での確認手順

1. 別ユーザー・別ブラウザで同じデータを開く。
2. Aが数量2→1（数量のない納入先・プラントでは名称等）を保存。
3. Bは再読込せず数量2→3等を保存し、指定の排他エラーが表示されることを確認。
4. DBにはAの内容が残り、Bの変更や同時に編集した関連行も保存されていないことを確認。
5. Bが検索画面等から最新データを開き直し、Aの内容を確認して再保存できることを確認。
6. 納入先、プラント、ブランド構成、機器構成、機器明細、個体管理で実施。競合のない登録・更新・削除も確認。
