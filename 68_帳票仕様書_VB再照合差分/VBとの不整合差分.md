# 単体・結合MDとVBの不整合差分

確認日：2026-10-07。対象は[単体65](../65_帳票単体テスト仕様書_Web版/MCM帳票_単体テスト仕様書_Web版.md)、その同一コピーの[単体66](../66_帳票単体テスト仕様書_Excel版/MCM帳票_単体テスト仕様書_Web版.md)、[結合67](../67_帳票結合テスト仕様書/MCM帳票_結合テスト仕様書_Web版.md)。元の仕様書・Excel・アプリは変更していません。

「明確な不整合」は受領VBの実装条件と期待結果が食い違うものです。Webで意図して変更した取得方法や、VBに存在する不具合を再現しないための改善期待は含めません。現行本番VBが受領コードと同一版かは別途確認が必要です。

## 差分一覧

| ID | 優先度 | 対象 | 不整合 |
| --- | --- | --- | --- |
| D01 | 高 | 結合：C10、INT09-001 | 一覧系の参照出力を一律に許可し、1002Pの例外を落としている |
| D02 | 中 | 単体：2001P-3、末尾の訂正説明 | 店舗見積書類の5・6番目の役割がVBと逆 |
| D03 | 高 | 単体：3001P-16、3005P-12 | 製番「*」の条件を、どちらの契約の解約か特定せず記載している。取引先解約として準備すると抽出条件と矛盾する |
| D04 | 中 | 単体：1003P-5 | 解約日が空の更新でも、解約欄の全項目に値が入ると要求している |

同じ原因で複数の項番に影響するものは1項目にまとめています。D03の2ケースは、両帳票に同じ値が伝わる観点を残し、削除や統合は不要です。

## D01：依頼一覧出力は参照権限の例外

### 修正前

結合C10：

> 一覧系は起点利用許可で参照出力。

結合INT09-001：

> 一覧系は起点画面の利用を許可された参照者が出力できる。

単体1002P-15は「参照のみ権限では依頼一覧出力が非活性、帳票を取得しない」であり、両仕様書の期待が衝突しています。

### VBの根拠

- [Mcm1003uScreen.Designer.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/20_CONSUMER/MCM1003U/Mcm1003uScreen.Designer.vb)：145行、`IraiIchiranSyutsuryokuButton.AuthorityIsThrough = False`。
- [CPCoreUserControl.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/10_FRAMEWORK/CONTAINER/CPCoreUserControl.vb)：199〜213行で参照権限時の制御を開始し、268〜275行で上記フラグがFalseのボタンを非活性にします。
- [CPSettingInfo.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/10_FRAMEWORK/INFO/CPSettingInfo.vb)：22行、権限制御の初期値はTrue。

MCM1003Uの実効画面権限が参照で、通常の権限制御を有効にした条件の判定です。見積作成（1002U）の権限だけを見て、1003Uの権限と同一扱いしないでください。

### 修正案

```text
参照権限で出力できる帳票を一律に扱わず、起点画面のボタン制御で判定する。
1002P：MCM1003Uの実効権限が参照なら「依頼一覧出力」は非活性。
作成なら、対象データがある条件で出力できる。
1001P、0001P、3001P／3005P、3002P／3003P、3004Pの参照出力は
各起点のVB権限制御と対応する単体ケースに従って個別に判定する。
```

**反映先：**結合C10、INT09-001。単体1002P-15はこの点では訂正不要。67の環境確認手順Q06にも1002Pの例外を追記すると誤解を防げます。

**Webへの影響：**受領Webの[Mcm1003uController.java](../../mcm-web/src/main/java/com/daifuku/mcm/controller/Mcm1003uController.java)130行以降の出力起点には作成権限チェックがなく、[画面](../../mcm-web/src/main/resources/templates/mcm1003u/index.html)371行のリンクにも非活性条件がありません。Webで出力できる現状をVB準拠の正解として採用せず、単体1002P-15で不具合として検出する方向です。実権限マスタと直接取得側も含めた実機確認は未実施。

## D02：店舗見積書類のシート順

### 修正前

単体2001P-3は次の順序を要求し、「⑤⑥の入れ替わりがない」としています。末尾の訂正説明も同じ内容です。

```text
5：仕切原価（ハード）／ハードウェア保守明細
6：見積原価表
```

### VBの根拠

[Mcm2001pConstant.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/30_CUSTOMER/MCM2001P/Mcm2001pConstant.vb)25〜26行：

```vb
Public Const SHEET_INDEX_GENKA_BRAND As Integer = 5
Public Const SHEET_INDEX_HARD_MEISAI As Integer = 6
```

[Mcm2001pExcel.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/30_CUSTOMER/MCM2001P/Mcm2001pExcel.vb)87〜100行で、それぞれの位置へハード明細と見積原価表のデータを書き分けています。複数ブランド・期間では3〜7番目の組を追加する処理も同じ定数を使います。

### 修正案

```text
ブランド1つ・期間1つでは7シート。
役割順は、見積総括表→保守見積総括表（原価）→保守見積書
→保守仕様明細目録→見積原価表→ハードウェア保守明細→ソフトウェア保守費明細。
5番目は見積原価表、6番目はハード明細。
複数ブランド・期間では、3〜7番目の組もこの順に繰り返す。
正確なシート見出し名は正式VB原紙で別途確認する。
```

**反映先：**単体2001P-3、末尾の訂正説明。2001P-4・44の複製組の順序もこの基準で照合します。結合INT05の取得物を照合するときは、修正後の単体基準を使います。

**Webへの影響：**現行の[Mcm2001pConstants.java](../../mcm-web/src/main/java/com/daifuku/mcm/constants/Mcm2001pConstants.java)26〜27行はハード5・原価6です。提供Web原紙の現状に合わせて定数・MDがそろっていても、受領VBの役割順との一致とは別です。配備原紙とデータの書込位置を一緒に見直す必要があり、定数だけの入替は誤ったシートへの書込を招きます。正式VB原紙が未提供なので、原紙の見出し・印刷構成全体までは断定しません。

## D03：製番の「*」は関連ユーザー契約の解約日で判定

### 修正前

単体3001P-16は「対象月より前に解約された契約で、対象月も支払対象」を準備し、解約していない契約には「*」が付かないとしています。3005P-12も「解約後の月」の説明が同様に曖昧です。

起点が取引先契約の支払帳票なので、取引先契約の解約日として準備すると、解約後の月はそもそも支払ビューから除外されます。また、取引先が未解約でも関連ユーザー契約が解約済みなら、製番注記は付く場合があります。

### VBの根拠

[mcm_tk_siharai_v.sql](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/database/40_view/mcm_tk_siharai_v.sql)69行と86行は別の契約を使っています。

```sql
-- 製番に「* 」を付ける判定：UKA＝ユーザー契約
CASE WHEN TKK.TSUKI < NVL(UKA.KAIYAKU_DT, ...) THEN '' ELSE '* ' END
-- 支払対象に含める判定：TKA＝取引先契約
AND TKK.TSUKI <= NVL(TKA.KAIYAKU_DT, ...)
```

[Mcm3002uScreen.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/40_ETC/MCM3002U/Mcm3002uScreen.vb)165・177行で、同じビューの`HARD_SEIBAN`を両帳票へ渡します。

### 修正案

```text
支払月が取引先契約の支払対象条件を満たすデータを用意する。
その関連ユーザー契約の解約日と、支払月の日付TSUKIを比較する。
TSUKIがユーザー解約日より前：製番に「* 」なし。
TSUKIがユーザー解約日と同日または後：製番に「* 」あり。
ユーザー解約日がNULL：通常の支払月では「* 」なし。
両帳票の同じ対象行で、製番と注記が一致する。
取引先契約の解約日より後のTSUKIは対象外で、注記確認用の行にしない。
```

比較は単に「解約した年月」ではなく実際の`TSUKI`と解約日です。月途中の解約日と同月月初のTSUKIでは、同月でも注記なしになります。NULL時の代替上限日については原本条件に従います。

**反映先：**単体3001P-16・3005P-12の前提と期待結果。結合INT06-004はすでに両契約を分けており、主要な期待結果は訂正不要。単体の準備もこの結合ケースと合わせます。

## D04：更新依頼書の解約日欄は空欄

### 修正前

単体1003P-5の前提は「解約日が空」ですが、期待結果3では解約欄の「契約金額・支払月・解約日・契約書番号」の両方に値が出ると要求し、解約日を解約専用の1003P-13へ参照しています。

### VBの根拠

[Mcm1005uScreen.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/20_CONSUMER/MCM1005U/Mcm1005uScreen.vb)：

- 1313〜1333行：解約日なし、かつ直前に有効期間があると更新区分。
- 1421・1428行：旧期間の金額と支払回数を設定。
- 1431行：`kihonData.KAIYAKU_DT = Me.KAIYAKU_DTTextBox.Text`。
- 1434行：契約書番号は契約NOを設定。

更新時の入力解約日が空なので、旧契約欄の解約日も空です。旧期間の終了日などを代わりに印字する処理ではありません。

### 修正案

```text
更新区分では、新契約欄に選択期間の内容を表示する。
旧契約欄には直前の有効期間の金額・支払回数と契約NOを表示する。
解約日未入力の更新では、解約日欄は空欄。
解約日を入力したときの印字確認は解約区分1003P-6・13として別に実施する。
```

**反映先：**単体1003P-5の期待結果3と1003P-13への参照説明。1003P-14の新旧金額比較、結合INT03-002の期間所属比較はそのまま残します。

## 不整合とは別に、前提を具体化する点

### M01：金額4列の設定名を具体化する

単体3004P-28・29は「金額表示権限が1以上／0以下」とだけ説明しています。数値条件自体はVBと一致しますが、独立した金額表示設定を探してしまうおそれがあります。

[McmLogin_UserInfo.xml](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/20_COMMON/LOGIN/McmLogin_UserInfo.xml)17行で分類ID3の利用権限を取得し、[Mcm3004uScreen.vb](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/30_APPLICATION/40_ETC/MCM3004U/Mcm3004uScreen.vb)80〜84行で0以下の場合に4列を非表示にします。

単体の前提も結合INT09-002に合わせ、「担当者マスタの取引先契約関連（分類3）がなし／参照／作成」と具体化する案です。実環境の分類名は登録値を確認します。単体の課題Q05と結合のQ06は別一覧の番号であり、同じ番号の課題と取り違えません。

### M02：解約日を期間タブの項目として説明しない

単体1003P-6は「解約日が設定された期間タブを選択」と記載していますが、VBの発行区分は画面上段の契約共通`KAIYAKU_DTTextBox`で決まります。期間IDだけで解約区分になるのではありません。

「編集可能な契約状態で上段の解約日を入力し、対象期間を選択して契約発行」と書き換えれば、結合INT03-003とそろいます。既に状態が解約の契約を通常発行する手順とは分けます。これは期待する区分の訂正ではなく、操作説明の明確化です。

## 反映するときの順番

1. D01・D03の権限とデータ前提を先に訂正します。準備する利用者・契約が変わるためです。
2. D02・D04の期待結果と末尾の説明をそろえます。
3. M01・M02の前提を具体化します。
4. 65・66の同一MD、66の単体Excel、67の結合MD・Excel・環境確認手順を対応させます。仕様書だけ変更する場合も、現行アプリの不整合を合格条件にしません。
5. 項番・ケース数を保持したまま、更新後のExcel／MD一致を確認します。今回の差分は新規ケース追加やケース統合を要求するものではありません。
