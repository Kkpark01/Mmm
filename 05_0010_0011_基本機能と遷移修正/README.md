## 削除と04への影響

0010の管理者削除はVBの全関連データ削除に対応。誤ったIDで子データを消していたSQLを修正し、選択プラントの41関連表に対象を限定した。別プラントと契約を共有する場合は、他のプラントに影響させないため削除を中止する。途中で失敗した場合はトランザクションを取り消す。

04のメールキューが存在する場合、対象見積の送信待ちは送信対象から外し、送信中なら削除を中止する。送信済み履歴は保持する。新しいメール送信やDTS連携処理自体を追加したものではない。

## 大量検索の表示改善

検索SQL・条件・取得件数・並び順・数量計算は維持しています。VBと同様に検索時点の全件を一括取得します。納入先一覧は全件表示し、プラント・ブランド・機器は、選択した親に該当する行だけをブラウザー上に組み立てます。他の親に属する行は表示用データとして保持し、親の切り替えで追加のDB検索は行いません。ページ切り替えや取得件数制限はありません。

以前は選択していない親の行までHTMLで作り、非表示にしていました。この余分なHTML生成とブラウザー処理を減らしています。IDや数量は文字列として受け渡し、数値精度を保ちます。Thymeleafで安全にシリアライズし、一覧の文字は `textContent` で表示します。

ローカルH2＋Chrome、納入先300／プラント900／ブランド1,800／機器3,600行の同一合成データでの3回計測です。実測値は本番の所要時間を保証するものではありません。

会社でまだ検索自体が遅い場合は、検証環境で `logging.level.com.daifuku.mcm.controller.Mcm0010uController=DEBUG` を一時設定すると、4つの検索処理の時間と件数を記録できます。`plant` の時間には権限確認を含みます。`display_rows_ms` は表示用データの整形時間で、テンプレート処理・通信・描画は含みません。検索語や納入先名をこの計測ログへ出しません。ブラウザーの初期表示処理は開発者ツールの `performance.getEntriesByName('mcm0010u-render')` で参照できます（通信・最終描画を除く）。

SQL Serverの索引追加・SQL書き換えは行っていません。本番データ量やDB側の待ち時間が原因の場合は、会社の検証DBで計測してから次の対策を判断してください。全件取得・保持を続けるため、極端に多い件数ではメモリー使用量や通信量の負担は残ります。
