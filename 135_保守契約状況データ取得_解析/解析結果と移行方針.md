# 保守契約状況データ取得：解析結果と移行方針

## 1. 根拠と確度

対象は受領した「保守状況報告データ抽出.exe」。SHA-256は `1E42BCD4C3110BC04BC1EE180FCD7EF82527B44DE6545EC01BDDD32932E52150`。

実行せず、.NETのメタデータとIL（コンパイル後の命令）を読み取った。62処理の本体を取得。主要業務処理のデータ取得・Excel編集・画面イベント・スレッド・ログ・コメント表示・初期化の7クラスは、参照先を解決できている。一部の自動生成Myクラスには未解決のジェネリック参照があるが、本資料のSQLと出力処理の読み取りには含まれない。

旧.NETの参照を解析環境の.NET Frameworkに対応付けて読み取っている。実行互換性の確認ではない。元のソース・コメント・プロジェクトは未受領のまま。

Excel原紙は [今回受領版](../../検証記録/20261029_VBツール受領資料/VBツール/保守契約状況データ取得/保守契約情報報告（月別）デフォルトフォーム.xls) を使用。以前の受領版とはファイル内容が異なるため、今回受領版を移行の原紙とする。

## 2. 現行の操作と流れ

内部のフォーム定義にある操作ボタンは「開始」「終了」。抽出年月や対象店舗を入力する部品は確認できない。日時欄と処理状況のコメント欄がある。

1. 「開始」を押すと「処理を開始しますか？」を表示する。
2. 「いいえ」で中止する。「はい」で開始・終了ボタンを非活性にし、「データ取得処理中」と表示する。
3. 保守金額、契約サポートID数、保守契約数の取得を3つのスレッドで実行する。
4. 3処理の完了を待つ。いずれかの取得が失敗した場合は、異常をコメント欄へ表示し、通常のExcel編集へ進まない。
5. 成功時は「エクセルデータ編集中」と表示し、原紙への転記・保存・Excel終了を行う。
6. 「処理を終了しました」と表示し、ボタンを再び活性にする。

根拠：`メインフォーム.開始_Click`、`スレッド関連.ThreadStart`、`EXCEL関係.ExcelEdit`。実際のダイアログ表示・実画面での操作は未実施。

## 3. 抽出対象：実行日現在の契約

ファイル名は月別だが、SQLの条件は**実行日当日の契約状況**。過去の指定月を検索する処理はない。

| 条件 | 読み取れた判定 |
|---|---|
| 契約状態 | ユーザ契約 `MCM_UK_KEIYAKU.JOTAI = '2'` |
| 解約日 | 未設定、または日付部分がDBサーバーの当日以降 |
| 延長契約満了日なし | 契約満了日が未設定、または当日以降 |
| 延長契約満了日あり | 延長契約満了日が当日以降。通常の契約満了日へは戻らない |
| 契約期間 | 当日を開始日～終了日に含み、`YUKO_FLG = 0` の期間のうち、期間IDが最大の1件 |
| 製番期間 | 当日を開始日～終了日に含む製番のうち、製番IDが最大の1件 |
| 店舗 | 選ばれた契約期間の `IRAITENPO_ID` から店舗マスタへ内部結合する |

開始日・終了日・解約日・満了日は時刻を切り捨てて比較し、境界日を含む。期間・製番の終了日がNULLの行を無期限として扱う処理はなく、その行は範囲条件に一致しない。

最大値を採る対象は「ID」であり、「開始日が最新の行」への置換は同じ条件にならない。製番について確認区分や有効フラグを追加で判定するSQLもない。店舗マスタ・有効な期間・当日を含む製番が見つからない契約は、この内部結合では対象外。

3本とも同じFROM・JOIN・WHERE条件を使用する。DB側の `SYSDATE` と、Excelに書く月のPC側 `Now` は別の時刻源である。

## 4. 集計の意味

| 出力 | 現行の処理 |
|---|---|
| 保守金額 | 店舗名 `MEISHO4_NK` ごとに、選ばれた契約期間の `HOSYU_GKIN` を合計 |
| 保守契約数 | 店舗名とユーザ契約IDでGROUP BYした行を、店舗ごとに数える |
| 契約サポートID数 | 店舗名とサポートIDでGROUP BYした行を、店舗ごとに数える |

契約サポートID数は単純な契約件数と同じではない。同じ店舗の複数契約が同じサポートIDなら、GROUP BY後は1行となる。また、サポートIDがNULLでもGROUP BYの1行として返るため、無条件に `COUNT(DISTINCT SUPPORT_ID)` へ置換するとNULLの扱いが変わる。

SQLは店舗IDでなく店舗名でまとめている。同名の店舗を別集計に変更すると現行と異なる。現行は金額合計を文字列で受け取り、Int64へ変換している。金額が全てNULLとなる店舗などの扱いは実データで未確認。

## 5. Excelへの出力

| 項目 | 読み取れた内容 |
|---|---|
| 原紙の参照 | 現行の共有フォルダを絶対パスで直接指定。実行フォルダの原紙を探す処理ではない |
| 使用シート | `デフォルトフォーム` |
| 対象月 | PCの現在月を `MM` 形式でB2へ設定 |
| 店舗行 | ExcelのCells.Findで店舗名を検索して取得 |
| E列 | 保守契約数 |
| F列 | 契約サポートID数 |
| G列 | 保守金額 |
| 保存先として渡す文字列 | カレントディレクトリ＋`\`＋`MM月保守状況.xls` |
| 保存呼出 | `Workbook.Close(True, 保存先文字列, Missing)` の後に `Excel.Quit()`。明示的なSaveAs呼出はない |

原紙は使用範囲B1:G92、3行目が見出し、E92・F92・G92がそれぞれ4～91行の合計式。今回受領原紙のE4:G91には値・式が入っていない。行が見つからなかった場合の未転記を、ゼロ件と取り違えないようにする必要がある。

保存先の文字列と転記先は命令から確定できる。一方、Closeに渡したファイル名で実際に別名保存されるか、既存ファイル時の表示・動作は未検証。カレントディレクトリは起動方法によって実行ファイルの置き場所と異なる場合がある。

## 6. そのまま移植すると問題になる点

### 移行のために必須

1. **OracleからSQL Serverへの接続変更**：現行はOracleClientと埋め込み接続文字列を使用する。新MCMの接続先・認証を外部設定へ分離する。旧認証情報は引き継がない。
2. **SQLの方言変換**：`TRUNC`、`SYSDATE`、`TO_CHAR`をSQL Server用へ変換し、日付の境界とNULLの扱いを維持する。現行は参照専用で、DB更新はない。
3. **テーブル定義の確認**：最新WebソースのMcm2006uRepositoryは `MCM.MCM_UK_KIKAN` と `YUKO_FLG` を使用している。古いSQL Server用CREATE TABLE資料はdboスキーマで、同テーブルのYUKO_FLGも記載されていない。古い資料だけで実DBの構造を確定しない。
4. **原紙の参照先変更**：固定された旧共有フォルダへの依存を外し、今回受領した原紙をツールと一緒に配置できる形にする。

### 結果を取り違えないために対応が必要

- **3集計の対応付け**：現行のExcelEditは金額一覧を順に処理し、契約数・ID数を同じ配列番号で取り出す。SQL Serverで店舗名の並びが変わる可能性があるため、同じ店舗名をキーに照合して転記する。
- **店舗名の加工差**：金額側は「プロジェクトチーム」「カスタマーステーション」を除去する。件数側はその前に半角空白も除去し、加工後の名前が切り替わる箇所で件数を確定する。加工前の店舗名を失わず、テンプレート上のどの行に対応したか確認できる形にする。
- **Cells.Findの条件省略**：検索範囲がシート全体で、完全一致・部分一致等の引数を省略している。部・支店名や類似する店舗名との誤照合が起きないよう、店舗名列D4:D91に限定し、未一致・複数一致を検出する。名称の対応が確定しない場合は勝手にゼロ埋めしない。
- **未一致時の処理**：現行は店舗行が見つからないと転記ループを抜ける。その後も保存呼出と正常終了メッセージへ進むため、一部が空欄の帳票が成功扱いになる経路がある。移行版では保存前に全店舗の対応を確認する。
- **保存失敗の扱い**：SQL取得の例外処理はあるが、ExcelEditに保存例外を処理するcatchは見当たらない。原紙を変更しない別名保存と、失敗時のExcel終了・中途ファイルの扱いを実装する。

これらは内部コードから確認した処理構造と、その構造で起こり得る問題であり、利用者の現行環境で誤った帳票が発生したという確認ではない。

## 7. 再作成する場合の方針

元EXEを直接書き換えるのではなく、読み取った処理を根拠とする、保守可能なVB.NET等のソースと実行ファイルを用意する。

- SQL Server向けに実行日の有効契約を取得し、店舗ごとに3項目を集計する。期間ID・製番IDの選び方と金額の元列を維持する。
- 処理開始時の基準日を1つに固定し、3項目で共有する。月別という名前だけを理由に、過去月指定や月払い計算を追加しない。
- 3項目は同じ対象集合を使用する。取得・集計をまとめる場合も、Oracle用の抽出結果と比較してから採用する。
- ツール、設定、原紙をまとめて配布し、結果は実行ファイルと同じフォルダへ明示的に保存する。これは現行のカレントディレクトリ依存を解消する方針であり、現行コードと全く同じパス解決ではない。
- 原紙のシート、列、合計式を維持する。同名ファイルがある場合は無断で上書きせず、確認を出す。
- 取得件数、進捗、失敗理由を表示し、成功時だけ完了を知らせる。接続情報やパスワードはログに出さない。

共通仕様の画面・BaseExcelService規則はWebアプリの画面実装を対象としている。今回は既存の独立Windowsツールの解析であり、WebのControllerや帳票サービスは追加・変更していない。
