## 維持した動作

- 候補のSQL取得範囲、表示順、行番号とチェック送信値、見積NOの重複排除・連結順、選択ブランド順の条件反映を維持。
- 基本ブランドと店舗見積を別々のIN句にせず、誤った組の契約条件を混入させない。BigDecimalの桁表現の差も同じIDとして扱う。
- 同じ組の同じ明細に複数の条件行がある場合だけ、元の1組SQLで再取得し、取得順を扱う既存処理を維持。通常の一意なデータは一括取得だけで処理。
- 期間チェック、重複候補通知、未見積候補の選択不可、既存チェック復元、戻る、親画面・権限・世代の検査を変更しない。
- HTML・JavaScript・共通部品・DB定義は変更なし。「次へ」で契約のDB登録は行わない。

通常の契約条件取得は、ブランド数分のSQLを1回へ削減する。400組を超える場合と上記の重複データでは追加SQLが発生する。SQL実行計画・HTML描画・フォーム複製が主な待ち時間の場合は、それらの追加対応が必要になる可能性がある。

## 反映後の確認

1. 以前遅かった同じ契約・プラント・見積でMCM2007Uを開く。選択見積、ブランド、期間、PC・ブラウザーを記録する。
2. 「次へ」を押し、機器選定画面が表示されるまでの時間を記録。ブランド・構成・明細・個体、見積NO、初期チェックを変更前と比較する。
3. 「戻る」→選択を維持して次へ、別条件でブランドを変更して次へを実施。意図しない選択解除や前回候補の流用がないことを確認する。
4. 新規契約経路と既存契約の変更経路を分けて実施。「適用」後の契約内容も確認し、検証用契約以外を登録しない。
5. まだ遅い場合は同時刻の`MCM2007U step2Post`と`MCM2007U loadStep2`ログを確認する。必要ならブラウザーのNetworkでPOSTとGETを分けて計測する。

ログの主な項目：`copyMs`＝フォーム複製、`validationMs`＝検査と重複チェック、`candidatesMs`＝候補処理全体、`restoreMs`＝既存チェック復元、`termsMs`＝契約条件取得、`numbersMs`＝見積NO対応付け。Serviceの`koseiMs`には見積IDの準備も含む。Controllerの`lockWaitMs`は同一セッション同期区間への入場待ち。`reloaded=false`は前回候補を再利用した場合で、処理全体の成功／失敗を示すフラグではない。

各ログは対象処理内の時間だけで、GETのHTML生成・転送・ブラウザー描画を含まない。異常終了時の未完了区間は0等になる場合があるため、周囲の例外ログも確認する。権限、トークン、契約内容、添付、個人情報はこの計測ログへ追加していない。
