## 画面の名称

| 表示名 | 操作・意味 |
|---|---|
| 保守契約管理システムサポートID付け替え | 画面タイトル |
| 付け替え元サポートID | 上段の入力欄。最大7文字。入力後にTabで欄を離れると納入先を取得 |
| 付け替え元納入先 | 上段の参照欄。納入先ID：納入先名。複数の場合は「, 」区切り、納入先ID順。直接編集不可 |
| 付け替え先サポートID | 下段の入力欄。最大7文字。付替元と同じ値は不可。未使用の値でも使用可能 |
| 付け替え先納入先 | 下段の参照欄。付替先が既存の場合のみ表示。未使用IDでは空欄。直接編集不可 |
| 開始 | 左の大きなボタン。「開始確認」で「開始してよろしいですか？」を表示。ボタンはOK／キャンセル |
| 終了 | 右の大きなボタン。「終了確認」で「終了してよろしいですか？」を表示 |
| 画面下部のメッセージ欄 | 結果・入力エラーを表示する参照欄。入力エラー・正常完了の別ダイアログを待たない |
| log.txt | EXEと同じフォルダー。追記形式。今回の実行位置以降を確認する |

先頭0の自動補完、7文字ちょうどの必須判定、数字だけの判定はコードにない。試験は実在する7桁のIDを使うが、これらの未実装チェックを期待しない。

## 更新対象と照合列

対象選択は各表の **SUPPORT_ID＝付替元A**。契約状態・有効フラグ・PLANT_IDで対象を絞り直していない。付替先Bが既存でも、B側へPLANT_IDや契約を統合する処理ではない。

| 表（スキーマMCM） | 更新行を特定する主キー | 更新内容 |
|---|---|---|
| MCM_MA_PLANT | PLANT_ID | SUPPORT_ID＝B、DTSRENKEI_FLG＝0、更新日時・更新者 |
| MCM_UM_KIHON_MITSUMORI | UM_KIHON_MITSUMORI_ID | SUPPORT_ID＝B、更新日時・更新者 |
| MCM_TM_MITSUMORI | TM_IRAI_ID | SUPPORT_ID＝B、更新日時・更新者 |
| MCM_TK_KIKAN | TK_KIKAN_ID | SUPPORT_ID＝B、更新日時・更新者 |
| MCM_UK_KIKAN | UK_KIKAN_ID | SUPPORT_ID＝B、更新日時・更新者 |
| MCM_MA_NONYUSAKI | 上記の対象プラントが持つNONYUSAKI_ID | DTSRENKEI_FLG＝0、更新日時・更新者。SUPPORT_IDの付替えはない |

更新日時はLASTUPDATE_DT、更新者はLASTUPDATE_BY。更新者は設定したWindowsユーザー名または固定ID。日時は既存値以上の時刻を再利用せず進める。PLANTはフラグとIDの2回更新なので、「1秒だけ増える」等の固定差を期待しない。対象納入先は、複数プラントから参照されても1回更新する。

## DB確認の共通手順

実施者がSSMS等の読み取り専用照会で実施する。以下の3つの値を各ケースの試験データ表の値へ置き換える。最初は実行前、次は実行後に同じSQLを実行し、結果を別名で保存する。各表は主キーごとに照合し、付替後にAだけで検索しない。途中で別の更新者が触れた場合は判定を保留する。

```sql
DECLARE @A nvarchar(7) = N'元ID';
DECLARE @B nvarchar(7) = N'先ID';
DECLARE @U nvarchar(7) = N'対象外ID';

SELECT PLANT_ID, NONYUSAKI_ID, SUPPORT_ID, DTSRENKEI_FLG,
       LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_MA_PLANT WHERE SUPPORT_ID IN (@A,@B,@U) ORDER BY PLANT_ID;
SELECT UM_KIHON_MITSUMORI_ID, PLANT_ID, SUPPORT_ID, LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_UM_KIHON_MITSUMORI WHERE SUPPORT_ID IN (@A,@B,@U) ORDER BY UM_KIHON_MITSUMORI_ID;
SELECT TM_IRAI_ID, PLANT_ID, SUPPORT_ID, LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_TM_MITSUMORI WHERE SUPPORT_ID IN (@A,@B,@U) ORDER BY TM_IRAI_ID;
SELECT TK_KIKAN_ID, PLANT_ID, SUPPORT_ID, LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_TK_KIKAN WHERE SUPPORT_ID IN (@A,@B,@U) ORDER BY TK_KIKAN_ID;
SELECT UK_KIKAN_ID, PLANT_ID, SUPPORT_ID, LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_UK_KIKAN WHERE SUPPORT_ID IN (@A,@B,@U) ORDER BY UK_KIKAN_ID;
SELECT NONYUSAKI_ID, DTSRENKEI_FLG, LASTUPDATE_DT, LASTUPDATE_BY
FROM MCM.MCM_MA_NONYUSAKI
WHERE NONYUSAKI_ID IN
 (SELECT NONYUSAKI_ID FROM MCM.MCM_MA_PLANT WHERE SUPPORT_ID IN (@A,@B,@U))
ORDER BY NONYUSAKI_ID;
```

対象外Uは、対象プラントと納入先を共有しない既存IDを準備する。共有する納入先はSUPPORT_IDがA以外のプラントに紐づいていても、正当なフラグ更新対象になり得る。既存B側の納入先にも同じ注意が必要。

5つのSUPPORT_ID保有表は0件でもよい。ただしPLANTと納入先に対象がなければ正常実行の前提を満たさない。0件だった表の更新分岐を「確認済み」にせず、残る確認として記録する。存在を確認できないデータを新規登録して条件を作らない。

## メッセージと残る範囲

正常終了は下部「【開始】処理を終了しました」。log.txtには「コミット完了：更新を確定しました」、続いて「  END  」を含む行が追記される。日時と外側の【】はログの付加情報。正常終了のメッセージボックスはない。

途中の更新ログだけを成功判定にしない。更新途中失敗、ログ出力失敗、コミット結果不明、Webとの競合は単体5件の外にあり、[骨子](骨子.md)の結合・開発者向け候補へ引き継ぐ。旧仕様のOracleエラー文言や旧接続文字列を新MCMの期待値へ流用しない。
