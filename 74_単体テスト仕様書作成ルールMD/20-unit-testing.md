# 単体テストの確認観点・作成手順

## 1. 先に機能・条件分岐を一覧化する

画面定義、イベント、入力検査、Service、SQL、共通処理を対象機能から追い、次の表を作る。機能や分岐が存在しない観点まで架空のケースを作らない。

| 機能ID | 操作・機能 | 条件／境界 | 期待結果の根拠 | 単体項番 | 他工程の項番 | 未確認 |
|---|---|---|---|---|---|---|
| 対象内で一意 | 表示名・操作 | 判定を変える条件 | 版・ファイル・定義 | 対応ケース | 分担する場合のみ | 理由・確認方法 |

一覧からケースへ、ケースから一覧へ両方向で確認する。大量のケース数や対応項番の存在だけで網羅を宣言しない。

## 2. 適用観点

| 観点 | 主要な確認 |
|---|---|
| 到達・初期表示 | 正式な経路、既存／新規／参照、初期値、既定タブ、初期フォーカス、渡されたID、セッション期限 |
| 項目・レイアウト | 項目とラベル、開始位置、幅、文字・通貨・日付・区分名称、ボタンの過不足、余白・スクロール。承認済みWeb共通仕様との整合 |
| 入力・境界 | 必須／任意、空欄・空白・null、型、桁／バイト、符号、小数、最小・最大、範囲内外、貼付け、複数項目の整合 |
| 日付・期間 | 書式、存在しない日、うるう日、同日、開始終了逆転、月末／年跨ぎ、上限期間、過去／現在／未来、期間の連続・重複・空白 |
| 検索 | 条件なし／単独／組合せ、完全／部分一致、0・1・複数件、null、並び順、絞り込み解除、クリア、再検索 |
| 一覧・選択・編集 | 行／セル選択、ソート、親子フィルター、チェックON/OFF、選択伝播、未選定禁止、編集開始・確定・取消、キーボード、非表示行の保持 |
| 活性・権限 | 機能単位の参照／作成等、権限なし、状態・モード別の表示／非表示・活性／非活性、直接要求の拒否 |
| 登録・更新・削除 | 変更あり／なし、新規／既存、確認OK／取消、対象キー・件数、履歴、監査値、重複、整合違反、非対象データ保持 |
| 計算・丸め | 0、正負、金額上限、数量、単価、割引、端数、単位、税・月割り等の対象機能の実定義 |
| 状態遷移 | 申請・承認・差戻し・解約等の許可条件、遷移前後、禁止状態での再操作、同じ要求の再送 |
| 戻る・取消 | 未保存の警告、入力・選択の保持／破棄、子画面復帰、キャンセル、完了後の戻り先 |
| 添付・出力 | 許可形式・サイズ・同名、保存・取得・削除の所属キー、対象0件、出力条件、ファイル失敗、共有フォルダー・旧パス・Office差異 |
| 排他・再送 | 競合の検出、先行者保護、後行者の表示と件数、二重送信、再読込み・訂正後の復旧 |
| 異常・トランザクション | 不正入力、権限拒否、例外、保存途中失敗、ロールバック、DBと外部ファイルの確定単位、通知失敗時の状態 |
| 多件数・性能 | 代表件数・最大想定、全件／ページ範囲、選択・編集・追加、メモリー・応答。合格時間と環境条件は合意値を使用 |
| 帳票・バッチ等 | 対象抽出、設定値、起動条件、出力・ログ、0件、途中失敗、再実行、ファイル名／印刷条件。対象種別に応じて適用 |

## 3. 境界の選び方

確認済みの最小値L・最大値Uについて、L未満・L・内部値・U・U超過を代表する値を選ぶ。整数なら前後1、小数・日付・長さなら対象の単位で選ぶ。境界が包含か排他かを比較演算と定義から確認する。

例：根拠で0～24を許容する項目なら、空欄の扱い・0・23・24・25・負数・非数値を確認する。「24より小さい」という既存文言だけで24を不正にせず、実際の比較条件を確認する。この値は全項目の共通上限ではない。

UIのmaxlengthやdisabledだけでサーバー防御を確認済みとしない。直接POST／要求改変のテストは権限・CSRF等の前提を保持した専用環境で行う。受付けた後の対象ID・編集可能範囲の検査も確認する。

## 4. 条件分岐と失敗後の保護

if／switch／SQL条件だけでなく、共通例外、早期return、catch、トランザクション、非同期通知まで追う。条件が複数ある場合は個々の条件が結果を変える組合せと、意味のある複合条件を選ぶ。

重複・未選択・不正期間がある場合、表示文言だけでなく「後続処理を行わない」「次画面へ進まない」「DBへ保存しない」を確認する。クリック不可にしているため本来のエラー通知が出ない問題も確認する。チェックがOFFのままであれば十分、とは限らない。

更新失敗時は、対象外データ・先行利用者の保存値・監査情報・添付実体を保護する。DBロールバックが外部ファイル・メールも戻すと仮定しない。許可された障害条件が準備できない場合は開発者テスト／実施条件待ちとする。

## 5. データと工程の分担

状態・権限・期間・親子関連を満たすテストデータを準備し、初期値・操作後値・確認キーを控える。ビューの内部条件が未取得なら、抽出の正解をソースSQLだけで断定しない。

同じ前提操作の証跡は他工程と共用できるが、判定目的と対象版を明記する。共通部品の単体で検査済みでも、画面から呼ばれていること・対象項目に設定が適用されることを確認する代表ケースを残す。

## 6. 作成順

対象・資料の確定 → 機能／分岐一覧 → 前提データと実施条件 → 代表正常系 → 境界・異常・権限・失敗 → 既存ケースとの重複整理 → 根拠・工程分担 → 操作順確認 → MD／Excel化 → 品質検証。

正常登録で作ったデータが後続の更新・削除に必要なら、先行項番と初期化・復元手順を示す。他ケースの実行順を暗黙に仮定しない。
