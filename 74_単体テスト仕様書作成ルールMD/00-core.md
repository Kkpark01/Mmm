# 単体テスト仕様書作成：基本方針

## 1. 対象

新MCM Web版の単体テスト仕様書の作成・修正・レビューに使用する。画面だけでなく帳票、マスタ、検索、承認、バッチ等にも、存在する機能に応じて適用する。今回の「単体」は機能・画面の単体テストであり、メソッド単位の自動テストだけを意味しない。

| [20-unit-testing.md](20-unit-testing.md) | 機能・条件分岐・境界・異常の確認観点 |
| [30-vbnet-winforms.md](30-vbnet-winforms.md) | VB・共通処理・Webの根拠調査 |
| [40-md-output-format.md](40-md-output-format.md) | MDと既存単体Excelの対応 |
| [50-quality-assurance.md](50-quality-assurance.md) | 重複・網羅・根拠・Excel品質の確認 |

## 2. 優先するもの

利用者の今回の指示・承認済み要件／移行合意・プロジェクトの正式な規定を優先する。このMD自体を承認済み業務仕様とは扱わない。期待結果はVB・設計資料・共通仕様・関連定義から決め、Webコードは移行実装と操作経路の確認に使う。現在のWebの不具合を正しい期待結果にしない。

VBに既知不具合や不整合がある場合は機械的に再現しない。根拠の衝突で期待結果が変わる場合は、差異・該当ケース・決定が必要な点を要確認にする。UIの実際の表示名はDesignerやWebテンプレート等で確認する。

## 3. 開始時に確認する資料

対象IDと名称、資料版、対象範囲、VBと最新Webソース、共通処理、メッセージ・入力検査定義、DB定義、設計書、基準単体Excel、既存単体／結合／帳票仕様書を整理する。画面の実績や古い調査記録は、その版・前提が今回と同じか確認して使用する。

資料が不足していても独立して確定できるケースは作成する。未取得DB定義、未確定の環境設定・運用・性能合格値は埋め合わせない。実行に必要なテスト値を設計することと、実在する契約番号・担当者・DB行を創作することは区別する。

## 4. 単体と他工程の境界

単体には対象機能の入力・表示・選択・計算・許可・保存・失敗時の振る舞いを含める。1画面で複数テーブルを更新するからという理由だけで、保存判定を全て結合へ移さない。

結合は複数機能・画面・処理をまたいだデータや状態の引継ぎ・後続利用を追加判定する。帳票工程がある場合は単独の帳票内容や印刷設定を分担できるが、出力要求の許可・対象選択・0件時の画面動作を失わないようにする。排他・権限も工程名だけで除外せず、対象操作の基本保護と、複数利用者／後続機能での整合を分ける。

除外・統合・分担は元項番、理由、確認先の具体的項番を残す。確認先がないものは省略せず、分担待ちとする。

## 5. 状態の区別

「仕様から確認済み」「コード上に実装あり」「テスト実行済み」「実行合格」は別。未実施をOKにしない。対象外は工程分担の設定であり合格ではない。未確定の期待は要確認、前提が満たせず実行できないものは保留／未実施等、基準Excelの区分に従って管理する。

新規ケースの実績は空欄。改訂時の既存実績は無断で消去せず、対象版・旧期待に対する記録であることを保持する。期待を訂正したケースは旧OKを合格証拠として流用せず再判定を求める。

## 6. 作業・成果

対象機能から必要な依存へ調査を広げ、無関係なソース一括読込みや変更はしない。細かなパス・ツールは作業環境に合わせる。元のソース、VB、参考Excelを依頼なしに変更しない。

最終成果物は利用者指定のExcelを優先し、必要なMD・対応表・要確認事項を同梱する。AIやサブエージェントへの委任、有料サービス利用は明示的な依頼がある場合だけ行う。本ルールの品質確認を理由に自動委任しない。

完了報告は対象・ケース数・保存先・変更／分担・検証範囲・未確認事項を簡潔に示す。未検証の全機能網羅や実行合格を断言しない。
