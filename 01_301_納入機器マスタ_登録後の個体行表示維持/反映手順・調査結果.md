# #301 納入機器マスタ：登録後の機器個体行表示

画面で順に確認する場合は、[動作確認手順.md](動作確認手順.md)を使用してください。操作ごとの期待結果と、実環境での結果記入欄があります。

## 結論と最新版の状態

2026-09-10受領のsrcを基準に調査しました。登録済み機器のセット数を1→2に変更する、チケット記載の操作は、受領ソースに既に含まれる#301対応で正常でした。

追加確認で、新規の機器構成を選択して登録した場合には、個体2件が保存されても、先頭の別構成に表示が戻る問題が残っていました。今回の修正は、この残存ケースでも登録後の選択を維持する補完です。既存行のチケット再現手順と、新規行の残存不具合を区別して検証しています。

製品の変更対象は、src/main/java/com/daifuku/mcm/controller/Mcm0013uController.java の1ファイルだけです。

## 原因

1. 登録時は、編集中フォームのコピーをsaveWorkingへ渡して保存します。
2. 新規の機器構成には負数の仮IDがあり、保存処理でそのコピー内の行に正式IDが設定されます。
3. 元のコントローラはコピーをその場で渡して破棄し、保存前のフォームから選択IDを取得していました。
4. 保存前の選択IDが仮IDの場合、リダイレクトURLへ引き継がない条件になっていました。
5. 登録後はセッションをクリアしてloadFormで再読込します。選択IDが引き継がれない場合はHYOJIJUN先頭の構成を選ぶため、そこに個体が1件あれば1行表示になります。

今回再現した問題は、個体の保存漏れではなく、再表示する機器構成が切り替わる問題です。修正前テストでも、保存済みの対象構成のセット数2・個体2件を確認しています。

登録済みの構成では正式IDを既存実装が引き継ぐため、この問題は発生しませんでした。新規の構成でも、登録後にその機器を再選択すれば2行になることと整合します。

## 登録ボタンからOK押下後まで

1. セット数変更：syncKotaiForSetNum → 作業データに不足個体を追加 → 再表示。
2. 登録ボタン：JavaScriptでvalidateへ送信し、数量・必須項目等を検証。
3. 確認「登録を実施します。よろしいですか？」のOK：updateへ送信。
4. サーバー：作業データのコピーをsaveWorkingへ渡して登録。
5. 成功時：正式な選択IDを付けてリダイレクト → 保存済みデータを再読込 → 同じ機器構成の個体を描画。
6. 完了「登録を完了しました。」のOK：ダイアログを閉じるだけ。個体行を再生成・削除する処理はありません。

機器再選択時は選択IDを変更し、同じrender／activeIndividualsで表示します。再選択だけに特別な行復元処理があるわけではありません。

## 修正内容と影響範囲

保存用フォームのコピーと、その中の選択行への参照を保持します。保存成功後にその行の正式IDを取得し、既存のリダイレクト処理へ渡します。同名の構成が複数あっても名称で探さず、選択していた行そのものを追跡します。

- 登録済み行：従来どおり同じ正式IDを引き継ぎます。
- 新規行：採番後の正式IDを引き継ぎ、先頭の別構成へ戻ることを防ぎます。
- エラー時：従来どおり編集中フォームと仮IDを維持します。
- セット数変更、行生成、機器再選択、検証条件、DB更新、排他制御、トランザクション、メッセージ、HTML・JavaScriptの実装は変更していません。
