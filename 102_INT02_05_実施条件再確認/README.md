## 通常範囲から外す候補

### INT02-14：同じ期間に承認済み資料と審査中資料を混在させる前提

現在の本文にも、解約日未設定の通常の再申請では拒否され、管理者による専用データ準備が必要と書かれている。初見の実施者が通常の申請手順だけで用意できる前提ではない。

最低限の通常シナリオから外し、特殊な履歴混在データによる技術確認として残す案を推奨する。承認済み資料の保護全般を確認済みとする意味ではない。同じ期間の混在条件を、別期間の比較へ読み替えて本ケース合格としない。

根拠：VB `Mcm1005uScreen.vb:1113–1124`、Web [Mcm1005uService.java:1495](../../mcm-web/src/main/java/com/daifuku/mcm/service/Mcm1005uService.java:1495)。承認済み添付があり解約日が空なら再申請を拒否する。解約日設定時の例外経路まで含めて、あらゆる通常操作で絶対に作れないと断定したものではない。現在のケースはその準備経路を定めていない。

### INT04-16：同じ個体を含む承認済み見積2件

本文備考が「同じ個体を2件の見積に含める状態を、画面で作れるか未確認」「資料未準備なら未実施」となっている。重複を拒否する処理自体は存在するが、通常の準備経路が確定したことにはならない。

最低限の通常シナリオから外し、重複資料を準備できる管理者・開発者向けの確認として残す案を推奨する。「システム上絶対に作れない」とは断定しない。異なる個体2件で正常に進むことを、本ケースの代替合格にしない。

根拠：VB `Mcm2007uScreen.vb:222–259`、Web [Mcm2007uService.java:158](../../mcm-web/src/main/java/com/daifuku/mcm/service/Mcm2007uService.java:158)、[Mcm2007uRepository.java:66](../../mcm-web/src/main/java/com/daifuku/mcm/repository/Mcm2007uRepository.java:66)。

## 前提・手順を補えば残せる項目

### INT04-02・04・06・07・08・19：必要な個体数と採用状態が不足

02は機器を選んで登録するが、後続ケースが必要とする機器数まで指定していない。

- 04は「1つ目の明細に採用済み個体2件」「別の明細」を使い、採用個体数の違いからセット数1を期待している。
- 06・07は採用済み個体を外して、未採用個体を採用する。その未採用候補が元見積に必要。
- 08は採用済み個体を1つ外す。
- 19は1つ目と2つ目の明細で、それぞれ個体を外す。

02で任意の1明細・1個体だけを登録すると、このまま後続の手順を実施できない。対象ケース用の準備条件に、構成1件、明細2件、各明細の採用個体2件を明示する。06・07用には、1つ目の明細に未採用の候補個体1件も用意する。期間変更用の契約は本文どおり別契約を用意し、現在日を含む期間・終了日2か月以上先という条件も準備時に確認する。通常の新規作成自体は1明細・1個体でもよいが、後続用データと取り違えない書き方にする。

根拠：最新Excel各ケースD・E・F列、VB `Mcm2007u2Screen.vb:407–454`、Web [Mcm2007uService.java:171](../../mcm-web/src/main/java/com/daifuku/mcm/service/Mcm2007uService.java:171)、同244行付近のセット数再計算。元見積にない個体は、同263行の検査で採用できない。

### INT04-04～08・18・19：編集画面の「別ウィンドウ」表現

「MCM2007Uが別のウィンドウで開く／閉じる」と記載されている。Webの通常の編集・ウィザード遷移は同じタブである。画面を閉じるためにブラウザのタブを閉じると、手順の意図と違ってしまう。

「MCM2007Uへ切り替わる」「画面の『閉じる』を押下してMCM2006Uへ戻る」「『適用』後にMCM2006Uが表示される」とする。確認ダイアログの要否は各ケースの既存条件を維持する。

根拠：[共通仕様2.1・2.2](../../参照用/共通仕様/新MCM用_共通.md)、[Mcm2006uController.java:252](../../mcm-web/src/main/java/com/daifuku/mcm/controller/Mcm2006uController.java:252)、[Mcm2007uController.java:149](../../mcm-web/src/main/java/com/daifuku/mcm/controller/Mcm2007uController.java:149)。

### INT04-17：確認担当者Bの権限

前提はBにMCM3008Uの「利用できる権限」としか指定していない。参照権限だけでは「確認」が非活性になるので「更新権限」にする。AとBの担当者名が異なる条件は維持する。

根拠：[mcm3008u/index.html:408](../../mcm-web/src/main/resources/templates/mcm3008u/index.html:408)。

### INT04-15：ビュー定義未確認という保留理由を更新できる

参照用DB資料に `mcm_alert6_v.sql` と、その参照先 `mcm_alert_seiban_v.sql` が存在する。「ビュー定義が確認できないため」という理由は、今回の調査時点では解消できる。

資料の定義では、契約状態2、有効値0以下のうち期間IDが最大の期間を抽出し、製番の情報を外部結合する。製番0件なら最終製番・終了日はNULLとなる。解約日はNULLでもビュー内で9999/12/31に置き換えられ、検索側は製番終了日NULLを基準月初として判定する。

したがって「契約状態＝契約、最新有効期間あり、製番0件、解約日未設定、基準年月＝実施月、月数＝1」で、資料の定義上は検索対象となる。通常範囲から除外する必要はない。比較契約・全機器・全監査値の確認は省き、対象契約の表示と製番0件の保持に絞れる。

配備されたWeb側ビューがこの定義と同等かは未確認。準備担当者による表示確認または配備定義照合は必要であり、実DBで表示確認済みとは報告しない。

根拠：[mcm_alert6_v.sql](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/database/40_view/mcm_alert6_v.sql)、[mcm_alert_seiban_v.sql](../../参照用/MCM_javaコンバート用/MCM_作業用/MCM_作業用/database/40_view/mcm_alert_seiban_v.sql)、[Mcm3004uRepository.java:367](../../mcm-web/src/main/java/com/daifuku/mcm/repository/Mcm3004uRepository.java:367)。

### INT05-09：新規登録時の確認が手順・期待メッセージに不足

登録手順は登録確認1回、期待メッセージはMSG_0007G→MSG_0008Gとなっている。新規の取引先契約では機器個体の期限などを設定する確認MSG_0102がある。Web実装では新規確認に続いて通常の登録確認が出るので、両方で「OK」とする手順を明示する。

VB通常登録ではMSG_0008の表示行がコメントアウトされている。VB準拠の期待として完了通知を必須にせず、Webの追加完了通知と分けて記載する。保存・再検索の確認は残す。

根拠：VB `Mcm1005uScreen.vb:824–831,884–885`、Web [mcm1005u/index.html:1009](../../mcm-web/src/main/resources/templates/mcm1005u/index.html:1009)、[Mcm1005uController.java:648](../../mcm-web/src/main/java/com/daifuku/mcm/controller/Mcm1005uController.java:648)。

### INT05-11：破棄リンクがあることを前提へ補う

「未破棄」だけでは、必ず操作対象の「破棄」リンクがあるとは限らない。隣の10と同様に「状態が契約で、対象行に『破棄』が表示される」を前提へ明記すれば、実施者が手順5で止まるのを防げる。過去月の支払明細による拒否という確認は残す。

- INT02-12の図形不足xlsxは、準備担当者がファイルを加工して添付できる異常系。システム内に不正状態を作る条件とは異なるため、実施不能として除外する必要はない。

- INT05-19は最大期間が有効な条件に絞られており、INT06で外した「無効な期間しかない状態」は要求していない。
- 残る「ON／OFF」は「チェックを入れる／外す」へ、INT05-17・18等の「受領Web」は「Web版」へそろえる。これは実施条件の不成立ではなく、初見向けの表現補正。
