# MCM2006U：サポートID付替時の排他確認

133のサポートID付替ツールと、新MCMのユーザ契約内容画面（MCM2006U）を併用する場合の修正です。133を変更せず、Web版の対象ファイルだけを保存しています。

## 何が変わるか

現行VBのMCM2006Uは、期間のサポートIDや更新日時など、取得時の値を登録時に比較しています。一方、修正前のWeb版は契約本体の更新日時を確認していましたが、付替ツールは期間のサポートIDを更新しても契約本体の日時を変更しません。そのため、開いたままの画面が古いサポートIDを登録し直す可能性がありました。

修正後は、MCM2006Uを開いたときの各契約期間のサポートIDと更新日時を保持し、登録前に現在の期間情報と照合します。異なる場合、または期間の追加・削除があった場合は、既存の排他エラーを表示して登録を中止します。照合から登録までの間は、対象の期間をSQL Server上でロックします。

これは、**付替ツールによるサポートID変更を含むMCM2006Uの期間の競合への対応**です。現行VBが比較する全項目を移植したものではなく、すべての画面・他ツールとの競合を網羅した保証ではありません。

## 反映方法

1. `src/main` 内の3ファイルを、使用する最新Webソースの同じ場所に反映します。受領ソース `mcm-web/src` は直接変更していません。
2. `src/test` のテストファイルを同じ場所へ追加します。
3. ビルドして検証環境に配備します。付替ツールは133の実行用ファイルを使用します。133と134は別のファイルを対象としており、反映順は問いません。
4. 配備前に開いていたMCM2006U画面は、一度閉じて再度開いてください。古いセッションには比較用の情報がないため、登録時に排他エラーになります。

## 検証結果

- Webプロジェクトの別コピーに修正を反映し、Javaのコンパイルと対象テスト9件が成功。新規契約で既存期間の比較情報を要求しないことも確認しました。
- サポートIDだけが変わった場合、更新日時だけが変わった場合、期間の追加・削除、読込情報がない場合に、更新処理へ進まず排他エラーになることを確認。
- 情報が同じ場合は通常の登録経路へ進むこと、画面の作業データのコピー後も比較用情報が維持されること、DBの同じ行からサポートIDと更新日時を読み取ることを確認。
- ローカルSQL Serverの一時テーブルで、期間照合に使用するロック付きSELECTの構文と取得結果を確認。上記JavaテストはDBの呼び出しを模擬しており、実際のWeb画面とDBを接続した一連操作ではありません。

## 実環境で必要な確認

1. MCM2006Uで対象契約を開き、画面を開いたままにします。
2. **検証用のデータと権限で**133の付替ツールを実行し、その契約期間のサポートIDを変更します。
3. 先に開いたMCM2006Uで登録を行い、「他のユーザがデータを変更した可能性があります。処理をやり直してください。」と表示され、古いIDで上書きされないことを確認します。
4. 画面を開き直して新しいIDを確認し、変更が競合しない通常登録ができることを確認します。期間追加・変更・複数期間でも確認します。
5. 付替処理中と同時に登録する場合も、待機後に排他エラーになること、デッドロックや想定外のタイムアウトがないことを確認します。

実DBの型・データ・トリガー、実際の画面と付替ツールを使った同時操作は未確認です。ほかの画面・外部ツールも含む運用全体の競合防止は別途確認してください。

## 前回説明の訂正

最新受領srcのMCM0011U・MCM0012Uは、更新日時を前の値より進める実装がすでにあります。前回、これらを含むWeb側が単純に現在時刻を書き戻すかのように説明した点は正確ではありませんでした。ただし、別の更新処理には現在時刻を設定する箇所があり、全体の保証には追加確認が必要です。
