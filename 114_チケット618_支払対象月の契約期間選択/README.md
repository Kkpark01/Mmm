# チケット618：MCM3002U 支払対象月の契約期間選択

契約No：INT06-03

※上記はチケット指定の識別子です。実際の契約番号・切替月・実DBの値は未提示です。テスト項番を実契約番号として決め打ちしていません。

## 1. 不具合原因

**実環境での原因は未確定です。** 静的調査で確認できたのは、現Webの対象期間選択が配備済み `MCM.MCM_TK_SIHARAI_V` に依存し、アプリ側ではその行の契約期間を支払対象月と再照合しないことです。ビューが旧期間を返すと、その旧期間IDで単価を取得し、旧金額が帳票へ流れます。

VBの正式ビューには「同じ取引先契約の有効期間から、開始月が支払対象月以前の最大開始日を採用する」という条件があります。Webの計算処理・単価取得はVB関数と同じ経路です。配備済みビューの定義がこの条件を満たすかは、手元のsrcだけでは判断できません。

原因候補の優先順：

| 優先 | 原因候補 | 判定方法 |
|---|---|---|
| 1 | 配備済み支払ビューの期間選択条件がVBと異なり、旧期間または新旧両方を返す | 調査用SQLの3で採用すべき期間、4で実際のビュー行を比較し、1で定義を確認 |
| 2 | 新期間が旧見積の単価を参照している／新期間が未有効／支払対象月の設定が不成立 | SQLの2・5。新期間の `YUKO_FLG`、支払フラグ、`TM_TANKA_ID` → `TM_KIKAN_ID` と見積金額を確認 |
| 3 | 同一開始日の有効期間が複数ある、または確認済み製番の期間が重複している | SQLの3・6。最新開始日の候補が複数ないか、同一製番の有効期間が重なっていないかを確認 |

今回のコードは優先1の「支払ビューの期間選択への依存」を解消するものです。優先2・3に該当するデータの自動変更は行いません。

## 2. 原因となる処理箇所・金額取得元

| 処理 | 確認結果 |
|---|---|
| `Mcm3002uController.download` / `output` | 出力操作ごとに `searchForOutput` を呼び、DBから再取得する。以前の検索結果を金額の入力に使わない |
| `Mcm3002uRepository.search` | 変更前は支払ビューを支払月・区分で絞るだけ。採用する期間IDと期間開始・終了日もビューから取得 |
| `Mcm3002uService.searchForOutput` | 行の `TK_KIKAN_ID`・開始日・終了日ごとに金額を計算。キャッシュも1回の出力処理内に限定され、契約期間IDを区別する |
| `findRatePeriods` | `TK_KIKAN_ID` → `MCM_TK_KIKIKOSEI` → `MCM_TK_KIKIMEISAI` → `MCM_TK_TANKA.TM_TANKA_ID` → `MCM_TM_TANKA.TM_KIKAN_ID` → **`MCM_TM_KIKAN.SIKIRIGOKEI_KIN`** を取得 |
| `findPaymentDates` / `calculatePayment` | 選択された契約期間の支払ON/OFFと、紐づく見積期間の金額・期間から月配分し、端数と初回繰越を計算する。VB関数と同じ規則 |

契約画面の `MCM_TK_KIKAN.SIKIRIGOKEI_KIN` を単に12分割する方式への変更は、VBの金額取得・年払い・端数処理を変えるため採用していません。

## 3. 修正内容・反映方法

対象コードは以下の**Java1ファイル**です。

`src/main/java/com/daifuku/mcm/repository/Mcm3002uRepository.java`

- `SQL_SEARCH` を追加し、正式VBの支払ビューと画面検索をMCM3002U専用SQLとして明示。共有ビューの定義は変更しない。
- `search` の取得元を配備済み支払ビューから、この専用SQLへ変更する。
- `TK_KIKAN_ID` に対応する実テーブルの開始日を使い、開始月が支払対象月以前、`YUKO_FLG <= 0` の候補から最大開始日の期間を選ぶ。現在日付・最大ID・「新しいものを常に採用」は使用しない。
- 切替前月は旧期間、切替月以降は新期間だけが期間選択条件に一致するため、異なる開始日の新旧期間が同時に出る経路を除く。
- VBと同じく、状態「契約／解約」、支払ON/OFF、取引先解約日、ユーザー契約と確認済み製番、その製番の有効期間、名称の補完、並び順を維持する。
- `DISTINCT` はVBビューと同じ識別項目を含める。契約番号や製番の表示文字だけでまとめたり、異なる金額を合計／先頭優先で隠したりしない。
- 金額取得・月配分・端数・年払い・Excelの印字処理は変更しない。

このフォルダの `src` を利用中プロジェクトの `src` と同じ階層へ上書きしてください。`調査用SQL_契約期間と金額の確認.sql` はDB確認担当者向けの読み取り専用資料で、アプリ配置もビュー作成・変更も不要です。

`mcm-web/src` は最新受領版のまま保持しています。現存の番号付き修正版と同名srcの重複はありません。110・111・113との反映順序の依存もありません。ZIPは作成していません。

## 4. 影響範囲・残る確認事項

- MCM3002Uの検索経路、および同画面から作成する発注確認書・支払い明細の対象期間に影響します。
- 年払いも同じ期間抽出を使います。VBと同じ期間の選び方を適用し、年払いの計算式や回数判定は維持します。
- MCM3002UのVB画面・Web画面は「年払い」「月払い」の2択です。独立した「日払い」「その他」の選択肢は見当たりません。回数が1なら年払、0またはNULLなら不明、それ以外は月払というVBの分類を維持しています。
- 支払ビューそのもの、他画面、契約期間の登録処理、単価の保存、DBデータは変更しません。
- 同じ開始日の有効期間が複数ある場合、VBの最大開始日条件だけでは1件に確定しません。最大IDを勝手に採用して隠さず、SQLの3で複数候補を確認して登録内容・仕様を整理する必要があります。
- 同じ製番に紐づく複数ユーザー契約・支払明細まで無条件に削減する修正ではありません。期間選択を直しても同一契約・同一製番が重複する場合は、SQLの4・6で元の識別IDと製番期間を確認します。
- 新SQLは関連テーブルと `MCM_TU_KEIYAKU_V` への参照を行います。実行ユーザーのSELECT権限、配備済み同期ビューとの整合性、SQL Serverでの実行可否・処理時間は未確認です。

## 5. 追加テスト観点（実施はしていない）

1. 月払い・新旧2期間・金額が異なる条件で、切替前月は旧期間の計算額、切替月は新期間の計算額となり、同一契約・同一製番が新旧期間で二重出力されない。
2. 切替月の翌月以降も新期間を採用する。将来開始の第3期間は、その開始月になるまでは採用しない。
3. 新期間が `YUKO_FLG > 0` の間は採用しない。有効化後に出力すると選択が変わる。単なる承認状態の値を独自の抽出条件に追加しない。
4. 1期間だけの月払い、年払い、複数回払い、初回支払の繰越、端数、見積終了日なしの計算が従来どおりである。
5. 支払月OFF、契約解約日、未確認製番、製番の有効期間外はVBと同じく出力対象にならない。
6. 月途中開始はVB同様に開始月で切り替える。終了日の境界と計算対象月はVB関数の扱いを維持する。
7. 同一契約に複数の異なる製番がある場合、正当な製番行を落とさない。同一開始日の複数期間や重複する確認済み製番は別途切り分ける。
8. 期間切替後も旧金額が残る場合、新期間の `TM_TANKA_ID`・見積期間・見積仕切合計を照合する。契約画面の表示金額だけで期待額を決めない。
9. 発注確認書・支払い明細の両方を確認し、帳票間で期間の選択が一致する。支払い明細の整数丸めは従来どおりである。

## 6. 想定される再現・確認手順

事前データの作成操作は実機未確認のため推測を含みます。ここでは**登録済みの該当契約を使用する前提**で記載します。

1. DB確認担当者が、調査用SQLの `@TargetContractNo` と `@SwitchMonth` に実契約番号と切替月の月初日を設定する。実行結果の3で、切替前月は旧期間ID、切替月は新期間IDとなることを確認する。
2. 同担当者が2・5・6で、月払い、状態「契約」、新旧2期間が有効、両月の支払ON・OFFなし、確認済み製番の有効期間内、かつ新旧の計算元となる見積金額が異なることを確認する。旧・新の期間ID・計算元・期待額・製番を控える。
3. メニューの「支払い明細出力指示」を開く。「支払い月」に切替前月を `yyyy/MM` で入力し、「月払い」を選び、「出力」を押す。
4. **今回取得した**発注確認書と支払い明細を開く。対象の取引先のシートで、実契約番号と製番が一致する明細を探し、旧期間から計算した期待額であることを確認する。
5. 同画面の「支払い月」を切替月に変更して「出力」を押す。新たに取得した両帳票で、新期間の期待額、旧期間の金額なし、新旧期間による同一契約・同一製番の二重出力なしを確認する。前月のファイルを見間違えないよう保存先・ファイル名を区別する。
6. 修正前のビューが旧期間を返していたのか、新期間が旧見積へ紐づいていたのかはSQLの3～5で判定する。再現できない場合は、出力時の支払月・区分、契約／期間ID、確認済み製番、配備済みJARの版、SQL結果と例外があればサーバーログを控える。
