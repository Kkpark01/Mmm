# 実施順序と準備チェック（第5版）

## 各ケースの基本順

1. 利用者・権限・対象ID・契約状態・関連データを準備し、変更前の画面／読取DBを控える。
2. 正規画面で必要な変更を保存する。発行と保存が一体の場合は、その発行操作で保存する。
3. 保存後の対象を検索または選択して出力する。
4. 生成完了と新しいファイルの取得を確認する。支払帳票はZIPを展開して両ファイルを開く。
5. 開けた帳票を、同じ対象IDの保存値・再表示・検索結果と照合する。
6. 結果・証跡を記録し、権限・異常フック・データを必要に応じて復元する。

「内容を確認→出力できるか確認」の順では実施しない。取得できなければ、その失敗を記録し内容確認は未実施とする。単体の正常出力・取得が確認できた帳票から結合を始め、単体の書式・計算等の実績は対応表で参照する。単体全ケースの合格を無条件の開始要件にはしないが、当該結合で必要な機能・データ・出力が未成立なら保留または前提不成立として理由を記録する。

拒否・入力不備・0件・生成失敗では、通知・ファイルを返さないこと・保存値の維持を確認する。成功ファイルが存在しないので、内容照合へは進まない。過去に取得したExcelと今回のファイルは、取得時刻・対象・保存場所を分ける。

## ケース間の推奨順

これは作業の推奨順であり、ケース番号順に同じ契約を更新し続ける手順ではない。A/B等の記号は各ケース内の呼称で、別ケースの同名データとの共有を意味しない。全51件の実施対象を下表に一度ずつ記載した。

| 順 | 区分 | 対象項番 |
| --- | --- | --- |
| 1 | 通常の業務連携 | INT01-001〜004、INT02-001〜005、INT03-001・002・004・008・003、INT04-001〜003、INT05-001〜003、INT06-001〜007、INT07-001〜005・007、INT08-001〜006 |
| 2 | 不正要求・入力不備 | INT03-005、INT05-006 |
| 3 | 異常注入と復旧 | INT01-005・006、INT03-006・007、INT05-004 |
| 4 | 権限変更と同時更新 | INT09-001・002・004・005・006 |

1の通常業務連携には承認後の再発行拒否・0件遷移も含む。専用データでフローを完結させる。準備できたフローから進めてよいが、下記の明示的依存は守る。

## ケース間の依存とデータの扱い

| 対象 | 先に整えること／実施順 | 後続を妨げない扱い |
| --- | --- | --- |
| INT01・INT02 | 登録済み依頼が前提のケースは、正規登録で対象を準備する。INT01-001のデータを使う場合は親ID・状態を確認してから開始 | 新規・数量変更・複製・複数取引先は原則別データ。新規成功で必要な登録経路を先に確認 |
| INT03-002 | 旧有効A・無効Xが存在し、新Bは未登録。手順内でBを作成して保存→発行 | 既に作成したBを再追加して期待と異なる期間を作らない |
| INT03-004・008 | 未承認で発行可能→発行・取得→添付登録→申請→他利用者の承認または差戻し | 承認と差戻しは別の専用契約・期間を使う。差戻し直後の状態を先に記録し、再発行後の状態と混同しない |
| INT03-003 | 解約日未入力・編集可能な専用契約を用意 | 同じ契約を共有するなら編集・更新の確認後に実施し、解約日ありの状態を後続へ持ち込まない |
| INT04-003 | **INT04-002で未連携Aを検出・証跡採取した後に**Aを正規DTS登録する | 登録でAが消えるため、INT04-002を再実施するときは別の未連携データを準備。実運用マスタを安易に削除して戻さない |
| INT05 | 作成中→発行で見積状態へ進む。ロールバックケースは別の作成中見積を用意 | 成功ケースで発行済みになった見積を、そのまま作成中前提のINT05-004に使わない |
| INT06-002・004 | 新Bは未登録で準備。解約条件変更は正常支払の確認後、専用データで実施 | 期間追加・解約・月OFFにより別ケースの対象が消えないよう、ケース別契約・支払月を用意 |
| INT06-007・INT08-006 | 二人が同じ検証DBで同じ対象を扱う。Aの検索・証跡を先に確保し、Bの保存を後に行う | 3002Uは出力時DB再抽出、3004Uは検索済み結果保持。両者の期待を混同しない |
| INT07 | ON／再ON→差分出力、解除→保存→出力、新期間追加→前後出力の順 | ON継続と再ONのデータを分ける。期間追加で旧期間の翌年対象が変わるのでINT07-007は専用契約で行う |
| INT07-005 | 対象6機器→DB登録用帳票生成・取得→原ファイル保管→外部取込 | 出力が未取得・取込先未確定なら取込へ進まず保留。Excelで保存し直したファイルを取込原本として使わない |
| INT09-001・002 | 起点画面を利用できる状態と初期値を確認してから権限を変更 | テスト後に元の権限へ戻し、必要な再ログイン・再表示を行う。前提の利用不可を他ケースへ持ち込まない |
| INT09-004・006 | A/B両者が旧画面を開く→Aが保存→Bが旧画面から発行→拒否→B再表示→正規発行 | 拒否後に最新値を読み込み直す。Bの試行入力を再発行時に再適用せず、Aの保存値と照合 |
| INT09-005 | Aが申請前の編集画面を保持→別担当が申請→Bが審査・承認→Aが旧画面から発行 | 承認済み・解約日なしの専用期間を使い、通常編集ケースと共有しない |
| 異常注入ケース | 正常出力経路の確認→変更前採取→一回だけ失敗→失敗後の保存状態確認 | 必ずフック解除。復旧確認の出力取得・内容照合を先に完了し、他ケースへ移る。INT05-004は復旧後の正常発行を環境復元として確認する |

## 今回の訂正例

- INT03-004・008：「発行した帳票を添付」だけだった記載を、**発行→取得→開く→添付登録→申請**へ具体化。
- INT06-004：解約条件の保存後、出力操作を明記せず両帳票を照合していたため、**保存→対象月指定→出力→ZIP取得・展開→両帳票を開く→照合**へ訂正。
- INT02-005：取得済みを前提としながら手順でもAを取得していたため、前提を登録済みデータのみにし、取得は手順内へ統一。
- INT03-002・INT06-002：新期間が既に存在する前提で再登録していたため、**旧期間のみ準備→新期間作成・保存→出力**へ統一。
- INT09-004：期待にある「再表示後の正規発行」に対応する操作を追加。
