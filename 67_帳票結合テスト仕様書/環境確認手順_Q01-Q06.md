[結合テスト仕様書](MCM帳票_結合テスト仕様書_Web版.md)の「仕様書課題一覧」と対応します。環境確認が済んでも、52件のテストを実施したことにはなりません。

## 最初に確認すること

アプリを動かすPC／サーバー、DBを置くサーバー、添付ファイルを置く場所は別々です。ブラウザーで開くURLだけでは、DBや保存先は判断できません。

| 確認項目 | 現在のsrcの設定 | 実環境での確認方法 |
| --- | --- | --- |
| 環境指定がないとき | local | 起動ログの「使用環境」を見る |
| localの添付保存先 | `C:/opt/mcm/upload` | アプリを実行するPC上の場所。ブラウザーを開いたPCとは限らない |
| devの添付保存先 | `\\ILCM-SYSDEV\uploadfolder\MCM` | 実行サーバーから共有を確認する |
| local・devの標準DB接続先 | SQL Server：`ILCM-SYSDEV:1433`、DB：`SYSDEV` | 起動ログとSSMSで照合する。**localでもDBは検証用共有DBにつながる設定** |
| prod | DBと保存先を環境変数で指定 | 配備担当者に設定値を確認する。未定の値を検証用で代用しない |

これはsrcの初期値です。外部設定ファイル・環境変数・起動引数で上書きされている可能性があります。パスワードは確認記録に書きません。

1. ローカルならEclipseのコンソール、サーバーなら配備担当者が保管する起動ログを開きます。
2. `[MCM起動設定] 使用環境`、`DB接続先（設定）`、`添付保存先`を控えます。ログが見つからなければ配備担当者へ確認します。
3. 起動に使っている外部`application*.yml`、環境変数、起動引数も担当者に照合してもらいます。prodでは`MCM_DB_URL`・`MCM_FILE_UPLOAD_PATH`が対象です。
4. **起動ログは設定値の表示であり、接続成功・ファイルアクセス成功の証明ではありません。**以下の実確認と組み合わせます。

### SSMSでDBを確認する共通手順

1. 検証環境の接続情報をDB担当者から確認します。本番へ接続した場合はテストデータを登録しません。
2. SSMSで検証SQL Serverに接続し、対象データベースを選択して「新しいクエリ」を開きます。
3. 下のSQLを実行します。`ILCM-SYSDEV,1433`はSSMSでの**サーバー指定**で、DB名ではありません。現在のsrcのDB名は`SYSDEV`です。
4. 結果がアプリの接続先と一致しているか確認します。名前付きインスタンス・別名等で表示が異なる場合はDB担当者に確認します。

```sql
SELECT @@SERVERNAME AS サーバー名,
       DB_NAME() AS データベース名,
       ORIGINAL_LOGIN() AS 接続ログイン;

SELECT name AS スキーマ名
FROM sys.schemas
WHERE name = N'mcm';
```

以下のSQLは参照用です。`mcm`は対象スキーマ名に合わせます。「Invalid object name」はDB・スキーマ・配備・参照権限を切り分けてから判断します。エラーを消すために別DBの同名テーブルへ切り替えないでください。

## Q02：添付保存先と外部取込先を確認する

### 添付保存先

**確認先：配備／サーバー管理担当者と検証担当者。**

1. 共通手順で、稼働アプリの実際の保存先を控えます。
2. **アプリを実行しているPC／サーバー**から保存先が存在するか確認します。PowerShellの例は読み取りだけです。`$attachmentRoot`を起動ログの実値に置き換えます。

```powershell
$attachmentRoot = '\\ILCM-SYSDEV\uploadfolder\MCM'
Test-Path -LiteralPath $attachmentRoot -PathType Container
Get-Acl -LiteralPath $attachmentRoot | Format-List Owner, AccessToString
```

3. サービス／JARを実行するWindowsアカウントを配備担当者に確認します。共有アクセス権と保存フォルダのアクセス権の両方を、そのアカウントで確認してもらいます。上のコマンドは操作中の利用者として動くため、成功してもアプリの権限を証明しません。
4. MCM1005Uの専用テスト契約・期間へ小さな確認用ファイルを追加して登録します。別の利用者も、対象契約の参照権限を持つ状態でリンクから取得します。可能なら別PCからも確認します。
5. 対象期間IDを入れて保存記録を確認します。`0`のままでは対象データは得られません。

```sql
DECLARE @periodId bigint = 0; -- テスト対象のTK_KIKAN_IDに置き換える

SELECT TK_TENPU_ID, TK_KIKAN_ID, TENPUFILE_NK, DIRECTORY, SHONINJOTAI
FROM mcm.MCM_TK_TENPU
WHERE TK_KIKAN_ID = @periodId
ORDER BY TK_TENPU_ID;
```

6. `DIRECTORY`はフォルダ名ではなく**ファイルまで含むフルパス**です。新規保存は設定ルートの下に`torihikisaki/契約ID/期間ID/UUID/ファイル名`を作ります。記録された実ファイルの存在を、実行サーバーで確認します。

```powershell
$attachmentFile = 'SQLのDIRECTORYの実値に置き換える'
Test-Path -LiteralPath $attachmentFile -PathType Leaf
Get-Item -LiteralPath $attachmentFile | Select-Object FullName, Length, LastWriteTime
```

7. 既存添付も1件確認します。保存先設定を変えても、旧ファイルの移動とDBの`DIRECTORY`は自動では直りません。現在の設定ルート外、ファイル不在、権限不足はそれぞれ別に記録し、移行担当者へ渡します。この確認SQLでパスを更新しないでください。
8. テスト後の確認用ファイルは、運用上許可されている場合に画面の削除操作で片付けます。共有フォルダの既存ファイルを直接削除しません。

**判定：**新規添付と移行済み既存添付をアプリ経由で取得でき、名称・内容・所属が正しく、別利用者／PCでも共有されること。読み取り・登録・削除の必要権限を実行アカウントが持つこと。フォルダが存在するだけでは合格にしません。

## Q05：配備ビューと対象データを確認する

ビューはDB内の「抽出条件を保存した一覧」です。手元のSQLファイルと、検証DBに配備された定義が同じとは限りません。

**確認先：DB／開発担当者。**SSMSで正しいDB・スキーマを確認後、配備定義を読み取ります。

```sql
SELECT s.name AS スキーマ名, v.name AS ビュー名, m.definition AS 配備定義
FROM sys.views AS v
INNER JOIN sys.schemas AS s ON s.schema_id = v.schema_id
LEFT JOIN sys.sql_modules AS m ON m.object_id = v.object_id
WHERE s.name = N'mcm'
  AND v.name IN (
    N'MCM_TK_SIHARAI_V', N'MCM_TK_TENKEN_BASE_V', N'MCM_TK_TENKEN_V',
    N'MCM_TU_KEIYAKU_V', N'MCM_UPS_V',
    N'MCM_ALERT1_V', N'MCM_ALERT2_V', N'MCM_ALERT3_V', N'MCM_ALERT4_V',
    N'MCM_ALERT5_V', N'MCM_ALERT6_V', N'MCM_ALERT8_V', N'MCM_ALERT9_V'
  )
ORDER BY v.name;
```

結果が見えない／定義がNULLの場合は、メタデータ参照権限や暗号化の可能性もあります。不存在と即断せず、DB担当者へ確認します。Webの点検抽出は主に`MCM_TK_TENKEN_BASE_V`とアプリの`search_tenken.sql`を使用し、予定登録タブは`MCM_MO_SAGYOYOTEI`を使います。旧版の同名ビューだけを比較して確認完了とはしません。

次の条件を、仕様書の「コードで確定した条件」と配備定義で照合します。Oracle原本の構文が同じではなく、SQL Server上で抽出結果が同じになることを確認します。

| 対象 | 主な照合点 |
| --- | --- |
| 点検 | 契約／解約、有効期間、ON・OFF、対象月と最新適用期間、個体管理。差分はON_DTの日付範囲 |
| 点検の翌年展開 | 次期間なし・個体管理・自動更新。点検月+12か月を解約日と比較し、元の点検月を撤去日と比較 |
| 支払 | ON・OFF、有効期間、最新適用期間、解約日、関連ユーザー契約・確認済み製番・製番の適用期間 |
| 契約差異 | 選択基準の検索日付が対象期間内かつ相手の検索日付より前。同日は対象外 |
| バッテリー | 期待寿命日と個体終息日、関連契約・個体の結合、寿命日NULL時の検索日、MC保守の有効最新期間 |

### 支払帳票の対象データを探す例

検索したい月の月初を指定します。例の日付は実データがある月に置き換えます。0件なら別月をむやみに試す前に、下の切り分けを行います。

```sql
DECLARE @monthStart date = '2026-10-01';

SELECT TOP (20) TK_KEIYAKU_ID, TK_KIKAN_ID,
       TK_SIHARAI_ID, TK_SIHARAIMEISAI_ID,
       UK_KEIYAKU_ID, KEIYAKU_NO, TSUKI
FROM mcm.MCM_TK_SIHARAI_V
WHERE TSUKI >= @monthStart
  AND TSUKI < DATEADD(month, 1, @monthStart)
ORDER BY TSUKI, TK_KEIYAKU_ID, TK_KIKAN_ID, TK_SIHARAIMEISAI_ID;
```

0件の切り分けは、DB担当者が対象契約を限定して、契約→その契約に属する期間→支払情報→ONでOFFでない支払月→関連ユーザー契約→確認済み製番と適用期間、の順で行います。親契約がない期間、関連ユーザー契約／製番がないデータは、支払情報だけあってもビューに出ない場合があります。対象を無理に出すためにビュー条件を緩めません。

**判定：**配備された抽出条件が確定仕様と同値で、各ケースの「含む対象A」「含まない比較対象B」を用意できること。1件の出力成功だけで全ビュー・境界条件の確認完了とはしません。

**証跡：**取得日・DB名付きの配備定義、照合差分、対象キー・月・抽出結果。全件抽出ではなく対象契約や月を絞って確認します。

## Q06：権限登録と画面動作を確認する

**確認先：担当者マスタ管理者・検証担当者。**管理画面はコード上「担当者マスタ（MCM3006U）」です。対象担当者を選び、利用権限欄の分類名と「なし／参照／作成」を確認します。画面の分類名はDB登録値も確認します。

1. 専用の検証利用者を、なし・参照・作成の各条件で用意します。対象機能に対応する分類を先に確認します。
2. 以下のSQLは登録内容の確認専用です。ログインIDを置き換えます。パスワードは取得しません。

```sql
DECLARE @loginId nvarchar(100) = N'検証利用者のログインID';

SELECT t.TANTO_ID, t.LOGIN_ID, t.TANTO_NK,
       b.KENGENBUNRUI_ID, b.KENGENBUNRUI_NK,
       k.RIYOKENGEN_KBN AS 登録値,
       CASE ISNULL(k.RIYOKENGEN_KBN, '0')
         WHEN '0' THEN N'なし'
         WHEN '1' THEN N'参照'
         WHEN '2' THEN N'作成'
         ELSE N'要確認'
       END AS 利用権限
FROM mcm.MCM_MO_TANTO AS t
CROSS JOIN mcm.MCM_MO_KENGENBUNRUI AS b
LEFT JOIN mcm.MCM_MO_TANTOKENGEN AS k
  ON k.TANTO_ID = t.TANTO_ID
 AND k.KENGENBUNRUI_ID = b.KENGENBUNRUI_ID
WHERE t.LOGIN_ID = @loginId
ORDER BY b.HYOJIJUN;

SELECT c.KINO_ID, c.KENGENBUNRUI_ID,
       b.KENGENBUNRUI_NK, c.RIYOKENGEN_KBN
FROM mcm.MCM_MO_KENGENKOSEI AS c
INNER JOIN mcm.MCM_MO_KENGENBUNRUI AS b
  ON b.KENGENBUNRUI_ID = c.KENGENBUNRUI_ID
WHERE c.KINO_ID IN (
  N'MCM1002U', N'MCM1003U', N'MCM1005U', N'MCM1011U',
  N'MCM0020U', N'MCM2003U', N'MCM2004U',
  N'MCM3002U', N'MCM3003U', N'MCM3004U', N'MCM3006U'
)
ORDER BY c.KINO_ID, c.KENGENBUNRUI_ID, c.RIYOKENGEN_KBN;
```

権限未登録の分類は画面で「なし」と補完される場合があります。登録値がNULLの行と0の登録行を混同しません。また、機能に対する実効権限は分類と利用権限の組合せで決まります。機能対応が複数ある場合は、1分類だけを見て断定せず開発担当者へ照合します。

3. 管理者が正規画面で設定した後、検証利用者はログアウト→再ログインします。利用者ごとに別ブラウザープロファイル等を使い、セッションが混ざらないようにします。
4. 各帳票についてメニュー・起点画面・ボタン・取得可否・DB更新の有無を記録します。直接要求の権限確認は開発担当者が仕様書の手順で行います。

| 対象 | コードから確定している主な条件 |
| --- | --- |
| MCM1001P | 起点1002Uの参照でも保存なしの出力は可能 |
| MCM1003P | 1005Uの通常契約発行は作成権限が必要。状態・承認等の条件も別途適用 |
| MCM2001P | 2003Uの新規見積発行は作成権限が必要。既に生成されたファイルの取得と新規発行は分けて確認 |
| 一覧系帳票 | 起点画面を許可された参照利用者が出力できる条件を確認。全帳票を作成のみとしない |
| MCM3004U／3004Pの金額4列 | 分類ID3の権限がなしなら非表示、参照・作成なら表示。独立した「金額表示ON/OFF」は設定しない |

金額表示は表示・出力時にDBを読む処理のため、同じセッション内の権限変更も別に検証します。他のメニュー等の確認で、再ログインを省略する根拠にはしません。

**判定：**実登録の分類・機能対応・対象利用者と、画面・帳票・更新可否が一致すること。ボタンが消えるだけで、直接要求の拒否まで合格にしません。
