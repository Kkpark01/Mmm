# 品質担保（ファクト確認・正確性検証）

結合テスト仕様書の事実の正しさを、作成とは独立した手順で検証する。
AIが「確認した」と述べることは、検証の代わりにならない。検証は、根拠資料との照合結果を記録して成立する。

## 1. 基本方針

- 仕様書内の事実（画面名、ボタン名、メッセージ、テーブル、カラム、遷移元、権限、挙動）は、すべて根拠資料に追跡できる状態にする。
- 根拠を示せない事実は、確定せず「要確認」にする。
- 作成した本人（同一のAIセッション）だけで検証を完結させない。別セッション、サブエージェント、または人が、根拠資料から再確認する。
- 検証したこと、していないことを区別して記録する。未検証を「問題なし」と報告しない。

## 2. 事実主張の分類

ケース中の記載を、根拠の種類で分類する。

| 区分 | 根拠 | 扱い |
|---|---|---|
| A 設計資料で確認 | 承認済み設計書、DB定義、メッセージ定義 | 確定 |
| B ソースで確認 | ファイル名と行番号・メソッド名を示せる | 確定（照合検証の対象） |
| C 実機で確認 | 画面キャプチャ、ユーザー回答 | 確定（確認条件を記録） |
| D 推測 | 上記で示せない | 確定しない。「要確認」にする |

備考・根拠欄に、区分A〜Cの根拠を書く。Dは「要確認」として記録する。

## 3. 検証の層

### 3.1 作成時（第1層）

- 各ケースの備考・根拠欄を、作成と同時に埋める。空の根拠欄を残さない。
- 検索で確認した事項（遷移元の網羅など）は、検索したキーワードと結果の件数を根拠欄に書く。
- 検索しきれなかった、確認できなかった事項は、その旨を書く。

### 3.2 機械検証（第2層）

文字列・構造で判定できる項目を、全件検査する。

- 項番：接頭辞＋3桁連番、欠番・重複なし
- 必須欄：項番、テスト項目、前提条件・操作／入力値、期待結果、期待メッセージ、備考／根拠が空でない
- D列の構成：【前提】【操作】【入力値】の3見出しがそろっている
- 結果入力列（G〜M）が空欄で出力されている。N列（数式）に値が出力されていない
- 表構造（Markdown）：全行の列数がヘッダーの15列と一致、`<br>` と `\|` の使用が正しい。最終ケース行が「9＋ケース数」と一致
- 禁止表現：10-case-writing.md 7.5
- 内部用語の混入：30-vbnet-winforms.md 7章（対象4列のみ）
- 遷移前提の曖昧表現：`等から`、`などから`、`リンク経由`、`ボタン経由`
- 不要なカタカナ読み、画面IDと画面名の対応
- 入力値の曖昧表現：「有効な条件」「当該データ」「任意のデータ」「対象データ」
- 期待メッセージ：5項目の書式、`メッセージID：MSG_xxxx、表示文言：要確認` の形式
- 「クリック」の残存（「ダブルクリック」を除く）
- 参照整合：「INT10-005で登録したデータを使用する」等の項番参照が、実在するケースを指しているか。移管対応表の項番が、実在するか。
- 分割・統合した項番が、移管対応表・要確認事項一覧に反映されているか

検査結果は、件数と該当項番を記録する。検査を実施できなかった場合は「判定不能」と記録し、合格としない。

### 3.3 照合検証（第3層：ファクトチェック）

仕様書の事実を抽出し、根拠資料と1件ずつ照合する。作成とは別のセッションまたはサブエージェントで行い、依頼時に「確認できない場合は推測せず、確認できないと報告する」ことを明示する。

| 照合対象 | 照合先 | 全件/抽出 |
|---|---|---|
| ボタン名、リンク名、列見出し | Designer.vb の Text / HeaderText | 全件 |
| 画面ID、画面名の対応 | 画面定義、メニュー定義 | 全件 |
| メッセージID、表示文言 | メッセージ定義ファイルと、実装の呼出箇所 | 全件 |
| ダイアログのボタン文言 | メッセージボックスAPIの実装 | 全件 |
| テーブル名、カラム名 | DDL、SQL、TableAdapter | 全件 |
| 遷移元、遷移先、遷移方式 | 画面遷移処理の呼出箇所をソース全体から検索 | 全件 |
| 権限判定 | 権限取得メソッドの呼出しと分岐 | 全件 |
| 引継ぎ項目 | 遷移元のDelivery設定箇所 | 全件 |
| 更新対象テーブルと監査列 | UpdateAll直前のコード | 全件 |
| 業務ロジックの期待結果 | 設計書・ソースの分岐 | リスク層別で抽出（4章） |

- 照合結果は、各項目について「一致」「不一致」「根拠を確認できない」のいずれかで記録する。
- 「不一致」「根拠を確認できない」は、仕様書を修正する。修正後、同じ照合を再実施する。
- サブエージェントの回答にある「確認できなかった項目」は、そのまま要確認事項一覧へ転記する。

### 3.4 人によるレビュー（第4層）

- 作成者以外の人が、リスクの高いケース（4章）を優先してレビューする。
- レビュー観点は、21-integration.md 13章の作成後レビュー項目を使う。
- 最初の1画面（パイロット）は、全ケースを人がレビューする。問題の傾向（例：遷移元の見落とし、表示名の取り違え）を把握し、第2・3層の検査項目に反映する。

### 3.5 実機確認（第5層）

- ソースで確定できないケース、実施区分「要確認」のケースは、10-case-writing.md 13章の手順で実機確認する。
- 確認結果と確認条件（データ状態の組合せ、確認行数）を記録する。

## 4. リスク層別の抽出

照合検証（3.3）で全件照合しない項目は、次のリスクが高いケースから優先して抽出する。

- 権限連携（表示・活性・遷移可否・処理可否）
- 排他制御、ロールバック、複数テーブル更新
- 承認・差戻しなど状態遷移
- 分岐が多い遷移先画面（遷移元区分、データ状態で挙動が変わる）
- 同種の機能が複数画面に別実装されているケース
- 実機確認で以前の結論が覆ったケース
- 要確認が付いているケース

抽出率は、第1回のパイロットの不一致率で決める。不一致が1件でもあれば、該当パターンの全件を再照合する。

## 5. 整合性の検証

- 移管対応表：単体テスト仕様書の移管元項番と、結合ケースの対応が双方向に追えるか。
- 重複：単体で確認済みの内容を、結合に転記していないか。結合ケース同士で、前提・操作・期待結果が重複していないか。
- 依存関係：依存元のケースが存在し、依存元の未実施・NG時の扱いが備考・根拠欄に書かれているか。
- 対象外機能：遷移先が対象外機能の場合、ケースとして起票されていないか。
- 件数：目次・集計の件数が、実際のケース数と一致するか。

## 6. 復元後の検証（Excel）

Markdownから基準ブックへ復元した後は、次を確認する。

- ファイルが開けること、全シートが存在し、シート順・表示/非表示が基準ブックと一致すること。
- 項番の欠番・重複がないこと。Markdownのケース数と、Excelの行数が一致すること。
- 全セル（数式セルを含む）に、`#REF!`、`#VALUE!`、`#NAME?`、`#DIV/0!`、`#N/A`、`#NULL!`、`#NUM!` がないこと。
- 最終判定（N列）の数式が、テスト結果（G列）と再テスト結果（K列）の同じ行を参照していること。全ケース行、追加行にも入っていること。
- 入力規則・条件付き書式が、全ケース行に適用されていること。
- 管理シートの数式が、新しいシート名・行範囲を参照していること。旧機能のシート名やサンプル固有の文字列が残っていないこと。
- セル内改行・折り返し・行高・列幅が崩れていないこと。
- 基準ブック（元ファイル）が変更されていないこと。作業前後で、サイズ・更新日時・ハッシュ値が同一であること。
- 一時ファイルが残っていないこと。
- Excelアプリケーション上の目視確認を実施したか。実施していない場合は、未実施と報告する。

## 7. 検証記録

検証の結果を、次の形式で記録する。

| 項番 | 検証層 | 検証内容 | 照合先 | 結果（一致/不一致/根拠確認不可/判定不能） | 対応 | 検証者 | 日付 |
|---|---|---|---|---|---|---|---|

- 要確認事項は、仕様書課題一覧に、該当項番、内容、確定できない理由、確認先を書いて集約する。
- 完了報告（00-core.md 8章）に、各層の実施状況と件数を含める。

## 8. ルール変更時の回帰確認

本Steeringのルールを変更した場合は、同じ画面（パイロット画面）で仕様書を再生成し、変更前後の差分を人が確認する。期待しない変化（根拠欄の欠落、禁止表現の再発、構成の変化）がないことを確認してから採用する。

## 9. 検証の限界

- 本手順は、仕様書の記載が根拠資料と一致することを確認するものであり、根拠資料自体の誤りや、実システムの不具合は検出しない。
- 全ケースの実機確認は想定していない。実機で確認していない内容は、区分BまたはAの根拠に基づく。
- 最終的な合否の妥当性は、人のレビューと実際のテスト実施結果で確認する。
