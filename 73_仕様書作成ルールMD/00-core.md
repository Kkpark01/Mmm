# 結合テスト仕様書作成 コアルール（常時適用）

## 1. 適用範囲

本ルールは、新MCMシステムの結合テスト仕様書を、ソースコード・設計資料を根拠として作成・修正・レビューする作業に常時適用する。
詳細ルールは次のファイルにあり、作業内容に応じて読み込む。

| ファイル | 内容 |
|---|---|
| 10-case-writing.md | テストケース各列の書き方、作業者向け表記、実機確認手順 |
| 21-integration.md | 結合テストの対象範囲、観点、構成、移管、レビュー |
| 30-vbnet-winforms.md | VB.NET(WinForms)ソース解析のノウハウ |
| 40-md-output-format.md | Markdown出力形式とExcel復元の仕様 |
| 50-quality-assurance.md | 品質担保（ファクト確認・正確性検証）の手順 |

## 2. 基本原則

1. 推測で仕様を確定しない。確認できない内容は「要確認」とする。
2. テスト作業者が、ソースや設計書を読み直さずに実施できる粒度で書く。
3. 期待結果は、画面・DB・ログ・出力ファイルの確認だけでOK/NGを一意に判定できる内容にする。
4. 既存成果物やAIが過去に生成した案を、単純コピーしない。根拠を確認して採用・修正・統合・分割・未採用を判断する。
5. 元ファイル（基準ブック、参考資料、既存仕様書）は上書きしない。指定された名称と保存先へ新規保存する。
6. AIの出力は確定仕様ではない。人が根拠と照合する前提で作成し、根拠を追跡できるようにする。

## 3. 創作禁止

次の内容を、根拠なしに追加・確定しない。

- 画面、画面ID、画面名、ボタン、リンク、入力項目、一覧列
- 機能、API、バッチ
- テーブル、カラム、キー、外部キー
- 権限、ロール、所属条件
- ステータス、状態コード
- メッセージID、表示文言
- テストデータの具体値
- 画面遷移、処理モード、ウィンドウ表示方式
- 登録・更新・削除・ロールバックの挙動

実データ固有値が不明な場合は、値を創作せず条件で記載する。

- サポートID＝機器構成が1件以上登録された既存プラントの値
- ログインID＝対象機能の更新権限を持つ有効ユーザー
- 付替え先＝付替え元とは異なる既存プラント

## 4. 資料の役割と優先順位

作業開始時に、入力資料を次の役割に分類する。

- 業務仕様の根拠
- 画面・データ連携の根拠
- 実装動作の根拠
- テストケースの根拠（既存の単体テスト仕様書など）
- Excel書式の基準（基準ブック）
- 参考例またはレビュー対象

資料間で内容が異なる場合は、次の順に確認する。

1. 本Steeringの確定ルール
2. 承認済みの要件定義書、基本設計書、詳細設計書
3. 承認済みのDB定義、メッセージ定義、画面定義
4. 対象ソースコード（画面、共通フレームワークのソースと設定を含む）
5. 単体テスト仕様書
6. 既存の結合テスト仕様書
7. 実画面または実行結果
8. 補足資料、調査メモ、過去の課題記録
9. AIが過去に生成した案、現在の未レビュー記載

プロジェクトで正式な優先順位が定められている場合は、その規定を優先する。
矛盾する資料のどちらかを、勝手に正としない。矛盾内容と対象箇所を「要確認」として一覧化する。

## 5. 「要確認」の扱い

- 根拠不足、資料間の矛盾、ソースで確定できない表示文字列は、推測で埋めず「要確認」と明記する。
- 「要確認」は、該当ケースの備考・根拠欄と、要確認事項一覧（仕様書課題一覧）の両方に記録する。
- 要確認があっても、確定できる範囲のケース作成は止めない。
- 根拠が確認できない場合の定型文：`【要確認】期待結果を確定できるソースまたは設計資料を確認できない。`

## 6. 作業開始前の確認

1. `.kiro/steering/` 配下のMarkdownを確認し、適用するファイル名と主要ルールを一覧化する。
2. 読み込めなかったファイル、存在しないパスを一覧化する。
3. 入力資料を4章の役割に分類する。
4. 必須資料が不足していても、確定可能な範囲は進める。

## 7. 調査時のツール使用

ファイル検索、ディレクトリ確認、内容検索、ファイル読み取りは、原則として専用ツールを使う。
シェルコマンドは、専用ツールで代替できない操作に限る。
この方針を理由に、調査範囲を狭めたり、確認すべきファイルの探索を省略したりしない。

## 8. 完了報告

完了時に、次を簡潔に報告する。

- 適用したSteeringファイル
- 参照した入力資料
- 出力ファイル名と保存先
- 作成・修正したシートとケース数
- 統合・分割・未採用とした元項番
- 要確認事項と該当項番
- 機械検証・照合検証の結果（50-quality-assurance.md）
- 目視確認の実施有無（未実施の場合は未実施と明記）
- 元ファイルを上書きしていないこと

検証を実施していない項目を、実施済みのように報告しない。

## 9. 適用確認

作業開始時に、次の形式で適用状況を示す。

```text
【Steering適用確認】
- 00-core.md：適用済み
- 今回適用する詳細ルール：{ファイル名}
- 競合または不足資料：{有／無。ある場合は内容}
```

自己申告だけで適用を保証したとは見なさない。成果物に対して50-quality-assurance.mdの検証を行い、遵守を確認する。
